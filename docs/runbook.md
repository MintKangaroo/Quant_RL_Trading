# 운영 런북

실제 돈이 걸린 시스템이다. **자동화보다 복구 가능성이 우선이다.**

2026-09-09 정책 도구 변경: `tools/promotion_gate.py`의 rc=2와 "승격 미지원"은
성과 불합격 판정이 아니라 구형 승인 경로가 닫혔다는 뜻이다. 새 평가를 돌려도 이
경로로는 활성화할 수 없다. `tools/promote_policy.py --off`는 해제 정정,
`--checkpoint … --dry-run`은 설정 변경 없는 점검이다. 보관된
`chain_20260830.sh`, `chain_r7_full.sh`, `chain_drl_r4.sh`를 복구 대상으로 다시
기동하지 않는다. 재개 조건과 새 증거 계약은 [RL 설계 §13](design/rl-training.md#13-승격)을 따른다.
이 변경은 이미 실행 중인 작업을 종료하거나 운영 config를 자동으로 고치지 않는다.

## 1. 배포 구조

GCP 를 기준으로 한다.

```
[Compute Engine VM]  워커 — Collector, Analyst, Selector, Executor, 회계
                     systemd 서비스로 관리, 자동 재시작
[동일 VM 또는 별도]  대시보드 (Flask, 읽기 전용)
[Persistent Disk]    data/ (raw + curated + agent_cache + events)
[Cloud Storage]      일일 백업
[Secret Manager]     LS API 키, Gmail 앱 비밀번호, Claude API 키
```

**DuckDB 는 단일 라이터다.** 워커만 쓰기, 대시보드는 읽기 전용 연결.
두 프로세스가 동시에 쓰면 파일이 깨진다.

VM 은 국내 리전(asia-northeast3)에 둔다. LS API 지연이 직접 슬리피지가 된다.

## 3. 장애 등급

에이전트가 죽는 것은 확실히 일어난다. 미리 등급을 정해두지 않으면
실제 장애 때 시스템이 예측 불가능하게 행동한다.

| 등급 | 대상 | 대응 |
|---|---|---|
| **치명** | store, Collector, Executor, 회계, Risk Analyst | **전체 정지.** 신규매수·매도 모두 중단 |
| **경미** | 개별 Analyst | 해당 Signal 을 중립 0 처리하고 계속 진행 |
| **경미 누적** | Analyst 3명 이상 사망 | **신규매수 중단**, 보유분 관리만 |
| **무관** | 리포트, 대시보드, ModelOps | 매매에 영향 없음. 로깅만 |

**리포트·대시보드 실패가 매매를 막아서는 안 된다.** 예외를 격리한다.

## 4. 킬스위치

### 자동 발동
- TWR 누적지수 기준 낙폭 30% 초과
- 주문 실패율이 임계 초과
- 데이터 품질 게이트 실패
- 회계 검증 실패 (NAV 불일치)

### 성격
**latch 방식.** 한번 걸리면 조건이 해소돼도 자동으로 풀리지 않는다.
사람이 수동으로 해제한다.

### 수동 발동·해제 절차

```bash
# 상태 확인 — 사유와 미확정 주문(submitting · 주문번호 없는 sent · 취소/정정 미확정)을 같이 보인다
.venv/bin/python tools/killswitch.py status                 # 기본 장부 data/_paper, --sandbox "" 면 주 창고

# 발동
.venv/bin/python tools/killswitch.py engage --reason "..." --by 이름

# 해제 — --confirm 필수. 미확정 주문이 남아 있으면 증권사 기록으로 확인한 증거를 --verified 로 적어야 풀린다
.venv/bin/python tools/killswitch.py release --confirm --by 이름 --verified "t0425 전체 조회에 없음 · 보유 수량 일치"
```

(2026-09-22 전까지 여기 적혀 있던 `python -m quant_rl_trading.executor.killswitch` 는 존재하지 않는 모듈이었다.)

`status` 는 미확정을 **오늘 거래일**과 **끝난 거래일**로 나눠 보인다. 끝난 거래일 것은 당일 유효 주문이라 이미 소멸했고 예산에도
안 잡히며 해제를 막지 않는다. 그래도 목록에 남는 이유: 국장 취소는 SC3 확인수량으로만 확정하므로(`execution-safety.md`) 상태
글자를 바꾸지 않는다 — 사람이 증권사 주문체결내역(CSPAQ13700, 그날 `OrdDt`, 다음 쪽은 헤더 `tr_cont=Y`)과 맞춰 본다.
2026-09-22 확인: 9/21 의 365550(원번호 13363, 891주)·005945(11279, 65주)는 체결 0 · 전량 "취소확인".

**"전송 결과 미확정" 으로 걸렸을 때**(`by=submission-unknown`): 사유에 주문 ID·종목·오류 내용이 있다. 증권사 주문 내역(t0425,
읽기 전용)에서 그 종목의 그날 주문을 찾는다. **없으면 미도착**이고, 있으면 체결·잔량을 장부와 맞춘다. 미확정 조각은 해제해도
**다시 보내지 않는다**(설계) — 그리고 킬스위치가 걸려 있는 동안 `risk_blocked` 된 그날의 조각도 해제 뒤 자동으로 다시 나가지 않는다
(`execution-safety.md` "킬스위치 해제 뒤 막힌 조각"). 그날 목표 비중은 다음 세션이 다시 계획한다.
미도착이 확인된 조각은 그 거래일이 끝난 뒤 `python tools/reconcile_backlog.py --confirm-not-received '<세션>|<종목>|<조각>'`
(미리보기) → `--apply` 로 닫는다. 그날 같은 종목 주문이 전부 우리 다른 조각 번호로 설명될 때만 닫힌다
(`execution-safety.md` "2026-10-04 미도착 확인 정정"). 안 닫으면 대사·추격 로그에 매번 경고로 남는다.

**한도 설정을 못 읽어도 매도는 막지 않는다** (2026-09-26). `risk/account.read` 의 `Limits`(설정 5개) 읽기가 try 밖에 있어
`ConfigNotFound` 하나가 `read` 전체를 실패시켰고, 호출부는 `budget=None` 으로 **매수·매도 구분 없이** 전부 `risk_blocked` 였다 —
청산이 필요한 날 설정 키 하나가 빠지면 한 주도 못 판다. 이제 한도를 모르면 `valuation_error` 로 남기고 **매수만** 막는다.
매도는 재고 검사(`Budget.check`)만 받는다. 다만 장부(`build_book`)를 못 만들면 재고를 모르므로 **여전히 전부 막는다** —
없는 주식을 팔 수는 없다.

해제 전 체크리스트:
- [ ] 발동 원인이 해소되었는가
- [ ] 현재 포지션과 실제 잔고가 일치하는가
- [ ] 데이터 품질 게이트가 통과하는가
- [ ] 미체결 주문이 남아 있지 않은가

## 6. 백업과 복구

| 대상 | 주기 | 보관 |
|---|---|---|
| `data/raw/` | 일 1회 | 90일 |
| `data/curated/` | 일 1회 | 30일 |
| 모델 체크포인트 | 학습 시마다 | 최근 10개 |
| 설정·가중치 이력 | 변경 시 | 영구 |

**`data/raw/` 가 가장 중요하다.** curated 는 raw 에서 재생성할 수 있지만
raw 는 그 시점을 놓치면 영구히 사라진다.

### 복구 시나리오

**VM 손실** → 새 VM + Persistent Disk 재연결 → systemd 재시작 →
킬스위치 상태 확인 → 잔고 대조 후 해제

**데이터 손상** → raw 에서 curated 재생성 → 리플레이 결정론 테스트 →
통과 시 재개

**중복 주문 의심** → 즉시 킬스위치 발동 → 증권사 체결 내역과 이벤트 로그 대조 →
client order id 중복 확인 → 원인 파악 전까지 해제 금지

**과거 회계 재계산** → 휴장일에 `tools/refresh_accounting.py --day` 를 손으로 돌리지 않는다. 호스트 정지·결손일(빈 칸을 새로 채운다),
크론 밖 장부(`_g1us_shadow` 등 — KR 시각 행이 섞인다)는 특히 금지. 필요하면 `scripts/refresh_accounting.sh` 와 같은 장부·같은 시장·
실제 세션이 있던 날만(2026-10-04 사고, `data/_quarantine/refresh-misfire-20261004/README.md`).

## 7. 스케줄

systemd timer 또는 cron. **워커 프로세스는 상시 실행**하고
내부에서 Session 타임라인을 따른다.

- 휴장일에는 Session 을 열지 않는다. 휴장일 캘린더는 `store` 에서 조회
- 서머타임 전환일 주의 (미장 시간이 1시간 이동)
- 프로세스 재시작 시 **진행 중이던 Session 을 이어받되 중복 주문은 내지 않는다**
  (멱등성, client order id)

### 7.1 크론 rc 규약 (2026-09-26)

**조용한 실패는 rc 로 내보낸다.** 블록 끝의 `echo` 가 rc 를 삼켜 전 단계가 실패해도 `rc=0` 이던 스크립트가 여럿이었다 —
그래서 15분 뒤 `run_daily` 가 어제 자료로 돌았다. 지금 규약:

| rc | 뜻 | 대응 |
|---|---|---|
| 0 | 정상. 또는 **정당하게 건너뛴 것**(휴장일 세션·정산 대조·지수 구성 재수집) | 없음 |
| 1 | **핵심 단계** 실패 | 사람이 본다. 시세·지수가 없으면 그 뒤 파이프라인을 돌리지 않는다 |
| 2 | 입력·사용법 오류 (모르는 단계 이름, 과거 `--day` 거부 등) | 명령을 고친다 |
| 3 | **판정 실패** — 거래일인지 아닌지를 모른다 | 주문을 내지 않았다. 원인을 고친 뒤 손으로 다시 돌린다 |
| 4 | 주문 대사는 맞는데 **정산금액 대조**가 틀렸다 | 원인 조사는 사람 몫. 주문 대사 rc 를 덮지 않되 묻히지도 않는다 |
| 5 | **계획했는데 안 보낸 조각**이 있다 (`run_session`·`run_paper.sh session`) — 같은 세션의 이전 시도가 거부·위험차단·철회로 끝나 중복 가드(`submit-<order_id>`)가 건너뛰었다 | 로그의 `계획했는데 안 보낸 조각` 줄에서 order_id 를 보고, 그 조각의 `orders.reason` 으로 원인을 가린다. 휴장일 거부(`rsp_cd=01410`)는 여기 오지 않는다 — 첫 거래일에 재전송되거나, 낡았으면 "낡은 휴장 거부" 로 로그에만 남는다 |

- **핵심과 부가를 가른다.** `collect_daily.sh` 는 시세·지수 실패만 `rc=1` 로 올리고, 거시·FINRA 같은 부가 단계는 요약 줄에만
  모은다 — 한 달에 몇 번 흔들리는 단계를 rc 로 올리면 `rc=1` 이 기본값이 되어 경보가 죽는다.
- **휴장 판정은 성공/실패를 값으로 구분한다.** `run_paper.sh session` 은 10(거래일)·11(휴장)로만 답하게 하고 그 밖은 `rc=3`.
  예전엔 `if ! python …` 이라 import 오류·venv 손상도 종료코드 1 = "휴장" 으로 읽혀 **거래일에 주문 없이 rc=0** 으로 끝날 수 있었다.
  `send_briefing.sh`·`wait_us_prices.sh` 도 같다 — 판정이 죽으면 "휴장"·"준비됨" 이 아니라 실패로 다룬다.
- **휴장일 거부는 재전송 가능, 다른 거부는 그대로 막는다** (2026-09-28). 9/24 추석에 `01410 모의투자 영업일이 아닙니다` 로 거부된
  70건과 9/28 재조정이 같은 세션(KR-2026-09-23)이라 중복 가드가 "이미 보냈다" 로 건너뛰었고 세션은 rc=0 이었다. 이제 휴장일 거부로
  끝난 조각은 **거부일 뒤 첫 거래일에, 그 세션이 그 시장의 최신 세션일 때만** 새 claim(`submit-<order_id>-retry-r<revision>`)으로
  다시 나간다(세션·`release_slices` 둘 다). 둘 중 하나라도 어긋나면 **낡은 휴장 거부** — 더 새 세션이 목표를 다시 정했거나 이미
  낡았다 — 로 노트·로그에만 적고 rc 는 올리지 않는다. 휴장 거부가 아닌 거부·철회로 건너뛴 조각이 있으면 rc=5 다. 대시보드 거부율 경보는 주문별 최신 revision 으로 세고 휴장일 거부를 분모·분자에서
  빼 따로 적는다.
- **휴장일엔 정산이 없다.** `settlement_check` 는 정산일이 그 시장의 거래일이 아니면 대조하지 않고 `rc=0` 으로 끝난다
  (추석 9/24 크래시, 9/25 브로커 0 ↔ 장부 4,928만원 거짓 불일치 — 9/22 체결의 실제 정산일은 9/28 이다). 거짓 경보는 진짜 불일치를 묻는다.
- **휴장일 재실행이 죽지 않는다.** 같은 세션을 다시 수집하면 `DuplicateIngestRun` 이 아니라 "이미 기록됨 — 건너뜀" `rc=0` 이고
  원천(KRX)을 다시 두드리지 않는다(`collect_index_members`). `daily_review` 는 휴장이면 **LLM 을 부르지 않고** `rc=0`
  (`--dry-run` 제외) — 크론이 월~금이라 추석 9/24·9/25 에도 돌아 새 세션 없이 LLM 값을 치렀다.
- **과거 스냅샷을 과거 사실로 적지 않는다.** `collect_consensus_naver` 는 원본이 날짜를 안 받고 지금 값만 주므로 기본 세션보다
  과거인 `--day` 를 `rc=2` 로 거부한다. 정말 필요하면 `--allow-stale` 이고, point-in-time 원본이 없는 결손은 백필할 수 없다.

정작 중요한 알림을 놓친다.

### 메모리 감시기 (`scripts/health_watch.sh`)

이 기계는 9,706MB 다. 전체 사용량이 9.0GiB 를 넘으면 곧 커널이 **아무나** 죽이고, 하필 대시보드나 수집이 죽어서 화면이
조용히 낡는다. 그래서 감시기가 먼저 **다시 돌릴 수 있는 것**을 골라 멈춘다 — 정지 목록(`STOPPABLE`)은 이어받기가 되는
것들뿐이다(시행 `trial_*`, 원피처 캐시 `diagnose_ic`, RL 캐시·백필·학습). 운영 부품(`v2_hmm_daily`·주간 `measure_ic`·
`run_session`)과 대시보드·수집은 넣지 않는다 — 멈추면 그날 기록이 빈다.

- **크론 15분마다 되살린다** (2026-09-26 복원). 저장소 안에 두는 이유도 같다 — 예전엔 `/tmp` 에만 있어 재부팅으로 사라졌다.
- **목록은 도는 작업을 따라간다.** 8월 목록 그대로였던 탓에 9/24 22:30 사용 9.4GB 에서 "멈출 수 있는 작업이 없다" 만 찍혔다.
  긴 도구를 새로 만들면 `health_watch.sh`(정지 목록)와 `memory_guard.sh`(희생 목록)에 같이 올린다.
- 로그 줄에 시각을 붙인다. 시각이 없으면 어느 회차가 그랬는지 뒤에서 못 찾는다.
