# 운영 런북

실제 돈이 걸린 시스템이다. **자동화보다 복구 가능성이 우선이다.**

---

## 1. 배포 구조

GCP 를 기준으로 한다.

```
[Compute Engine VM]  워커 — Collector, Analyst, Selector, Executor, 회계
                     systemd 서비스로 관리, 자동 재시작
[동일 VM 또는 별도]  대시보드 (Flask, 읽기 전용)
[Persistent Disk]    data/ (raw + curated + agent_cache + events)
[Cloud Storage]      일일 백업
[Secret Manager]     LS API 키, Gmail 앱 비밀번호, Claude API 키
```

**DuckDB 는 단일 라이터다.** 워커만 쓰기, 대시보드는 읽기 전용 연결.
두 프로세스가 동시에 쓰면 파일이 깨진다.

VM 은 국내 리전(asia-northeast3)에 둔다. LS API 지연이 직접 슬리피지가 된다.

## 2. 시크릿 관리

- **레포에 키를 절대 커밋하지 않는다.** `.env` 는 `.gitignore`, `.env.example` 만 커밋
- 운영 값은 Secret Manager, 로컬 개발은 `.env`
- pre-commit 에 시크릿 스캐너를 건다 (gitleaks 등)
- LS API 키와 Gmail 앱 비밀번호는 **분기마다 교체**하고 절차를 README 에 남긴다
- 실전 계좌 키와 모의투자 키를 분리 보관. 환경변수로 어느 쪽인지 명시하고,
  **부팅 시 로그에 크게 출력**한다 (모의인 줄 알고 실전을 돌리는 사고 방지)

## 3. 장애 등급

에이전트가 죽는 것은 확실히 일어난다. 미리 등급을 정해두지 않으면
실제 장애 때 시스템이 예측 불가능하게 행동한다.

| 등급 | 대상 | 대응 |
|---|---|---|
| **치명** | store, Collector, Executor, 회계, Risk Analyst | **전체 정지.** 신규매수·매도 모두 중단 |
| **경미** | 개별 Analyst | 해당 Signal 을 중립 0 처리하고 계속 진행 |
| **경미 누적** | Analyst 3명 이상 사망 | **신규매수 중단**, 보유분 관리만 |
| **무관** | 리포트, 대시보드, ModelOps | 매매에 영향 없음. 로깅만 |

**리포트·대시보드 실패가 매매를 막아서는 안 된다.** 예외를 격리한다.

## 4. 킬스위치

### 자동 발동
- TWR 누적지수 기준 낙폭 30% 초과
- 주문 실패율이 임계 초과
- 데이터 품질 게이트 실패
- 회계 검증 실패 (NAV 불일치)

### 성격
**latch 방식.** 한번 걸리면 조건이 해소돼도 자동으로 풀리지 않는다.
사람이 수동으로 해제한다.

### 수동 발동·해제 절차

```bash
# 발동
python -m lattice.executor.killswitch engage --reason "..."

# 상태 확인
python -m lattice.executor.killswitch status

# 해제 (확인 프롬프트 필수)
python -m lattice.executor.killswitch release --confirm
```

해제 전 체크리스트:
- [ ] 발동 원인이 해소되었는가
- [ ] 현재 포지션과 실제 잔고가 일치하는가
- [ ] 데이터 품질 게이트가 통과하는가
- [ ] 미체결 주문이 남아 있지 않은가

## 5. 일일 운영 체크

리포트에 자동 포함되지만, 사람이 봐야 하는 항목:

- 액션 반영률 (30% 미만이면 조사)
- 데이터 결측률
- 주문 실패 건수
- 슬리피지 실측 vs 예측 괴리
- NAV 와 증권사 잔고 대조 ⭐ **매일 확인한다.** 어긋나면 회계 버그다
- LLM 비용 누적

## 6. 백업과 복구

| 대상 | 주기 | 보관 |
|---|---|---|
| `data/raw/` | 일 1회 | 90일 |
| `data/curated/` | 일 1회 | 30일 |
| 모델 체크포인트 | 학습 시마다 | 최근 10개 |
| 설정·가중치 이력 | 변경 시 | 영구 |

**`data/raw/` 가 가장 중요하다.** curated 는 raw 에서 재생성할 수 있지만
raw 는 그 시점을 놓치면 영구히 사라진다.

### 복구 시나리오

**VM 손실** → 새 VM + Persistent Disk 재연결 → systemd 재시작 →
킬스위치 상태 확인 → 잔고 대조 후 해제

**데이터 손상** → raw 에서 curated 재생성 → 리플레이 결정론 테스트 →
통과 시 재개

**중복 주문 의심** → 즉시 킬스위치 발동 → 증권사 체결 내역과 이벤트 로그 대조 →
client order id 중복 확인 → 원인 파악 전까지 해제 금지

## 7. 스케줄

systemd timer 또는 cron. **워커 프로세스는 상시 실행**하고
내부에서 Session 타임라인을 따른다.

- 휴장일에는 Session 을 열지 않는다. 휴장일 캘린더는 `store` 에서 조회
- 서머타임 전환일 주의 (미장 시간이 1시간 이동)
- 프로세스 재시작 시 **진행 중이던 Session 을 이어받되 중복 주문은 내지 않는다**
  (멱등성, client order id)

## 8. 모니터링

- 헬스체크 엔드포인트: 마지막 Session 시각, 킬스위치 상태, 에이전트 생사
- 알림은 Gmail 로. 별도 채널을 늘리지 않는다
- 알림 조건: 킬스위치 발동 / 치명 등급 장애 / NAV 잔고 불일치 / Session 미실행

**알림을 남발하지 않는다.** 매일 오는 알림은 읽지 않게 되고,
정작 중요한 알림을 놓친다.

## 9. 변경 관리

- 운영 중 코드 변경은 shadow 를 거친다. 직접 배포 금지
- 배포 전 `pytest tests/invariants/` 통과 필수
- 배포 시 git commit hash 를 로그와 대시보드에 표시
- 롤백 절차를 문서화하고 실제로 한 번 연습해둔다
- **장 중에 배포하지 않는다**
