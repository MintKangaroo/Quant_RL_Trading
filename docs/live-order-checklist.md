# 실계좌 주문 배선 검증 — 점검표

`broker/ls_order.py`·`broker/fills.py`·`executor/pipeline.py` 는 전부 단위
테스트로 배선을 검증했다(httpx `MockTransport`). 그런데 **모의투자 키로는
주문 TR(CSPAT*)·잔고(t0424) 자체를 LS 가 막는다**
(`collectors/ls_client.py` `PAPER_ALLOWED_TR`). 실계좌 없이는 확인할 수 없는
마지막 구간이 남는다 — 그 구간을 사람이 지켜보며 최소 수량으로 확인하기
위한 절차가 `tools/verify_live_order.py` 다.

**이 문서는 실행 전 확인할 것, 실행 절차, 실패 시 되돌리는 법을 담는다.**
도구 자체의 안전장치(게이트·상한·확인프롬프트)는 그 파일 docstring 참고.

## 0. 이 문서로 확인되지 않는 것 — `executor/supervise.py` 배선

이 문서(와 `tools/verify_live_order.py`)는 **브로커 API 가 재호가·취소를
받아 주는지**(§3-1·§3-2)를 손으로 한 번 확인하는 절차다. 그것과
**시스템이 평소에 자동으로 재호가·취소를 하는지**는 다른 질문이다 — 후자는
`executor/supervise.py` 의 `register`·`step`·`close` 가 실제로 상시 루프에
배선돼 있어야 하는데, **2026-08-15 기준 그 배선이 없다**(모듈 docstring 참고,
`docs/milestones.md` M3 6번). 백테스트·shadow 는 `PaperBroker` 라 이 배선이
없어도 아무 문제가 안 보이므로, 이 문제는 **실계좌를 붙이기 전까지 드러나지
않는다.**

**그래서 이 소액 검증을 실계좌 정식 투입으로 확정 짓기 전에, 다음을 같은
작업에 넣는다:**

- [ ] `executor/supervise.py` 의 `register`/`step`/`close` 를 상시 워커
      루프에 배선한다(장중 반복 폴링 — `docs/runbook.md` §7 이 이미 전제하는
      모양). 세션당 한 번 도는 `session/daily.py`·`tools/run_session.py`
      안에는 못 넣는다 — 시간 축이 다르다.
- [ ] "세션을 돌리면 `step` 이 실제로 불린다" 를 확인하는 회귀 테스트를
      먼저 통과시킨다. 유닛 테스트 12개(`tests/executor/test_supervise.py`)
      는 모듈을 직접 부를 뿐이라 호출부 부재를 못 잡는다는 것이 이번에
      드러난 교훈이다.
- [ ] 위 배선이 된 뒤에 아래 §2 의 6단계(재호가)·3-1(부분취소)를 **자동
      경로로도** 한 번 더 재현해, 사람이 손으로 낸 정정과 시스템이 자동으로
      낸 정정이 같은 결과를 내는지 확인한다.

이 셋을 건너뛰고 실계좌를 정식 투입하면, 미체결이 나도 아무도 재호가·취소를
안 하는 상태로 돈이 오간다 — §2 의 수동 검증이 통과했다고 그 사실이
가려지면 안 된다.

## 1. 실행 전 확인할 것

- [ ] **계좌 잔고.** 최소 주문 금액(`--max-order-value`, 기본 10만원)보다
      충분히 크게 예수금이 있는지 LS 앱/화면에서 직접 확인한다. 이 도구의
      2단계(잔고조회)가 확인해 주지만, 그건 이미 토큰을 발급받은 뒤다 —
      미리 눈으로 보고 시작하는 편이 안전하다.
- [ ] **장 시간.** KR 정규장(09:00~15:30 KST) 안에서 돌린다. 도구가
      `is_regular_session` 으로 확인해 경고하지만, 넘기고 진행할 수도
      있으니 사람이 먼저 판단한다. 장외 시간에는 시세·체결 응답이
      예상과 다르게 온다.
- [ ] **킬스위치 상태.** `guards.killswitch_state` 가 `engaged` 면 이
      검증 자체를 미룬다 — 발동 원인이 아직 안 풀렸는데 실주문을 내는
      것은 검증이 아니라 사고다. 도구가 걸려 있으면 경고하고 확인을
      요구하지만, 걸려 있다면 애초에 진행하지 않는 것이 맞다.
- [ ] **config 값.**
      - `config/quant_rl_trading.yaml` 의 `execution.live_trading` 이
        지금 `false` 인지 확인한다(정상 상태). `--live` 를 줄 때만
        이 값이 `true` 여야 하고, 검증이 끝나면 **다시 `false` 로
        되돌린다.** 켜둔 채로 잊으면 다음 정기 실행(`run_daily.py`
        등)이 실계좌로 나간다.
      - `.env` 에 `LS_APPKEY`/`LS_APPSECRET` 이 **실전** 키로 채워져
        있는지 확인한다(모의투자 키로는 애초에 이 검증 자체가 안 된다 —
        도구가 client 단에서 막아 아무 일도 안 일어난다).
- [ ] **종목·수량.** 유동성이 충분한 종목(예: 시가총액 상위)으로,
      1주로 시작한다. 얇은 종목은 1주 매수도 호가를 흔들 수 있다.

## 2. 실행 절차

```
# 1) 드라이런 먼저 — 네트워크로 아무것도 안 나간다, 시세만 조회한다.
uv run python tools/verify_live_order.py --symbol 005930

# 2) 게이트를 켜되 여전히 드라이런 — 잔고까지 조회하고, 보낼 본문을 눈으로 본다.
uv run python tools/verify_live_order.py --symbol 005930 --live --dry-run

# 3) 실전 — 매 단계 y 를 눌러야 진행된다.
uv run python tools/verify_live_order.py --symbol 005930 --live
```

단계는 도구 안에서 다음 순서로 사람 확인을 거친다:

1. 토큰 발급
2. 잔고 조회 (t0424)
3. 시세 조회 (t1102)
4. 매수 주문 직전 요약(종목·수량·지정가·예상금액) → 확인 → 전송
5. 체결 조회 (t0425, 최대 5회 폴링) → (미체결 잔량이 있으면) 부분취소 테스트
6. (미체결이 남아 있으면) 재호가(정정) 테스트
7. 매도로 원복 → 확인 → 전송 → 체결 조회
8. 결과 — 로그와 LS 화면(잔고·체결내역)을 사람이 대조한다

**중단하면 포지션이 남을 수 있다.** 6단계 이전에 중단하면 매수 잔량이
계좌에 남는다 — §4 "실패 시 되돌리기" 를 본다.

## 3. 미확인 2건을 이 절차에서 어떻게 확인하는가

### 3-1. CSPAT00801(취소)의 `OrdQty` — "이번에 취소할 수량"인가 "잔량 전체"인가

참고 구현(`Invest_KOREA_Stock_Project/ls_kr_rl_trader/broker/order.py:473-489`,
`cancel_stale_live_orders`)은 취소 직전 브로커 잔량을 다시 조회해
`min(remaining, broker_remaining)` 으로 좁힌 값을 그대로 `OrdQty` 에 넘긴다.
그 값이 실제 잔량을 넘으면 거래소가 `01443=취소가능수량 초과`로 거부한다
— 즉 전량취소를 뜻하는 고정값이 **아니라** "이번에 취소할 정확한 수량"
이라는 뜻이다. `broker/ls_order.py` 의 `LSBroker.cancel` 은 이 해석을
그대로 따라 호출자가 넘긴 `quantity` 를 그대로 보낸다.

**부분체결 상태에서 일부만 취소해 보는 것이 유일한 확인법이다.** 절차:

1. `--quantity` 를 2 이상(예: 3)으로 주고, 즉시 전량 체결되지 않도록
   4단계 확인 직전에 지정가를 살짝 불리하게(매수라면 매도호가1보다
   낮게) 손으로 조정하고 싶다면 — 이 도구는 매도호가1을 자동으로
   쓰므로 즉시 체결될 가능성이 높다. 부분체결을 의도적으로 유도하려면
   유동성이 얇은 시간대·종목을 고르거나, 수량을 늘려 한 번에 다
   안 채워지게 한다.
2. 5단계 폴링에서 `partial` (일부만 채워짐)이 관측되면, 도구가
   "부분취소 테스트를 해볼까?" 를 묻는다. **잔량 전체가 아니라 그보다
   적은 수량**을 입력해 본다(예: 잔량 3주 중 1주만 취소).
3. 관찰할 것:
   - 취소 응답의 `rsp_cd`/`rsp_msg` — 성공이면 어떤 완료코드로
     오는지(00463 인지 확인 — `ls_client.py` `OK_CODES` 참고).
   - 취소 **후** 잔고/미체결 조회에서 남은 미체결이 정확히
     `잔량 - 입력한 취소수량` 인지, 아니면 전량이 취소됐는지.
   - 취소수량을 잔량보다 크게 넣어 보는 것도(도구는 자동으로
     `min(cancel_qty, remaining)` 으로 잘라 버리므로, 이 초과 케이스는
     `broker.cancel` 을 직접 호출하거나 이 문서의 절차를 손으로
     한 번 벗어나야 확인된다) `01443` 거부를 실제로 재현하는 방법이다.
4. 결과를 이 문서 §5 에 날짜와 함께 기록한다.

### 3-2. 재호가 목표가 — `lifecycle.decide(market_price=...)` 에 무엇을 먹여야 하는가

`executor/lifecycle.py` 의 `decide` 는 `market_price` 를 인자로만 받고
스스로 조회하지 않는다 — 호출자가 무엇을 넘길지가 실전에서 처음 정해진다.
후보는 최우선 매도호가(즉시 체결 우선)·최근 체결가(시세 지연 시 더
안정적)다. `tools/verify_live_order.py` 6단계는 미체결 상태에서 새 시세를
조회해 최우선 매도호가로 정정을 내 본다.

절차:

1. 4~5단계에서 미체결(부분·전량 모두 안 채워짐)을 만든다(3-1 과 같은
   방법 — 얇은 시간대이거나 수량을 늘린다).
2. 도구가 "재호가 테스트를 해볼까?" 를 물으면 y — 새 시세를 조회해
   최우선 매도호가로 지정가를 다시 계산하고, 보낼 본문을 먼저
   출력한다.
3. 관찰할 것:
   - 정정이 받아들여지는지(`rsp_cd`), 새 `OrdNo` 가 오는지 원래
     주문번호가 그대로인지(`_ord_no` 는 `OutBlock2` 우선, 없으면
     `OutBlock1` — 실제로 어느 쪽이 오는지 확인).
   - 정정 후 시세가 다시 움직여 그 가격에서도 안 채워지면, 최우선
     호가를 매번 새로 먹이는 방식이 실제로 체결을 당기는지, 아니면
     스프레드가 넓어 계속 못 채우는지.
4. 결과(어떤 가격 피드가 실제로 유효했는지)를 §5 에 기록하고,
   `pipeline.py`/`lifecycle.py` 호출부(아직 배선되지 않음)에 반영할
   근거로 남긴다.

## 4. 실패 시 되돌리기

| 상황 | 되돌리는 법 |
|---|---|
| 4단계에서 확인을 거부하고 중단 | 아무것도 안 나갔다. 되돌릴 것 없음. |
| 매수 전송 후 `BrokerError` (나갔는지 모름) | **재전송하지 않는다.** LS 화면에서 잔고·미체결을 직접 확인한다. 주문이 실제로 들어갔으면 미체결이나 보유수량으로 보인다 — 그걸 보고 7단계(매도)를 손으로 진행하거나 취소한다. |
| 매수 전송 후 `RejectedOrder` (확실히 거부됨) | 계좌에 영향 없음. 원인(`rsp_msg`)을 보고 재시도 여부를 판단한다. |
| 5단계 이후 미체결이 남은 채로 도구를 중단(Ctrl-C 등) | LS 화면에서 해당 종목 미체결을 확인하고 **수동으로 취소**한다. `broker.cancel` 을 예로 들면 `quantity` 에 잔량을 정확히 넣어야 한다(§3-1). |
| 체결됐는데 7단계 이전에 중단 | 포지션이 남는다. LS 화면에서 직접 매도하거나, 이 도구를 `--symbol` 그대로 다시 실행해 7단계까지 이어간다(도구는 매 실행마다 새 `order_id` 를 쓰므로 재실행 자체는 안전하다 — 다만 잔고 조회부터 다시 사람이 확인해야 한다). |
| 정정(재호가) 이후 원래 주문번호를 잃어버린 것 같음 | LS 화면의 미체결 목록에서 해당 종목·수량으로 다시 찾는다. `OrdNo` 가 바뀌었을 수 있다(§3-2). |
| `execution.live_trading` 을 켠 채로 검증을 끝냄 | **반드시 다시 `false` 로 되돌린다** — `config/quant_rl_trading.yaml` 수정 또는 store.config 오버라이드 원복. 다음 정기 실행이 실계좌로 나가는 것을 막는 마지막 방어선이다. |
