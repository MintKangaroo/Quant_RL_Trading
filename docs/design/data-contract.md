# 데이터 계약과 리플레이

핵심 원칙: **look-ahead는 코드리뷰로 못 막는다. 구조로 막는다.**

## 1. 저장 모델 — 이중시간, append-only

모든 팩트는 두 개의 시각을 갖는다.

| 필드 | 의미 |
|---|---|
| `valid_from` | 그 사실이 실제로 유효해진 시점 |
| `observed_at` | **내가 그것을 알 수 있었던 시점** |

`observed_at` 이 없는 행은 저장 자체를 거부한다.

UPDATE / DELETE 금지. 정정은 `revision` 을 올린 새 행으로 추가한다.

### 예외 하나 — 시각이 셋인 테이블

`macro_releases`(거시지표 발표)만 시각을 셋 갖는다.

| 필드 | 의미 |
|---|---|
| `scheduled_at` | **발표가 일어나는 시각. 미래일 수 있다** |
| `valid_from` | 우리가 그 사실(일정 또는 실측값)을 안 시각 |
| `observed_at` | 받아온 시각 |

발표 시각을 `valid_from` 에 넣고 싶어지지만 **그러면 안 된다.** 게이트의
lookback 창은 과거로만 열려서, 미래 `valid_from` 을 가진 행은 어느 창에도
안 걸린다 — "다가오는 일정" 을 영영 못 찾게 된다. 그래서 발표 시각은 별도
컬럼이고, 창은 언제나 과거로만 연다.

**기준시점은 발표 시각이 아니다.** KOSIS·ECOS 는 일정을 주지 않고 공표된
값만 준다. "2026년 7월 소비자물가" 는 7월 값이라는 라벨이지 7월에 발표됐다는
뜻이 아니다. 그대로 쓰면 7월 지표를 7월 1일부터 알고 있던 것이 되므로,
공표 지연을 더해 `scheduled_at` 을 계산한다.

### 공통 필수 컬럼

```
entity_id       KR:005930 / US:AAPL
valid_from      timestamp
observed_at     timestamp
source          출처
revision        0 = 원본, 1+ = 정정
ingest_run_id   어느 수집 실행에서 들어왔나
```

## 2. 폴더 구조

```
data/
  raw/                        원본 응답 그대로. 절대 삭제 금지
    ls_api/date=YYYY-MM-DD/
    dart/date=YYYY-MM-DD/
    news/date=YYYY-MM-DD/
  curated/                    정규화된 Parquet
    prices/market=KR/date=.../
    flows/
    fundamentals/
    fx/
    universe/                 그날의 상장종목 명단 스냅샷
  agent_cache/                에이전트·LLM 출력 캐시

```

`raw` 를 남기는 이유: 정규화 로직에 버그를 발견해도 원본에서 다시 만들 수 있다.
남기지 않으면 그 시점 데이터는 영구히 사라진다.

DuckDB는 **단일 라이터**다. 워커만 쓰고, 대시보드는 읽기 전용으로 연결한다.

## 3. 데이터 게이트 — 유일한 출입구

```python
store.get(table, as_of, entity=None, lookback=None) -> DataFrame
```

- 내부에서 `observed_at <= as_of` 를 무조건 적용
- 정정본은 `as_of` 이전 것 중 최신 `revision` 만 선택
- **참조 속성 예외** (2026-08-27): `TableSpec.reference_data=True` 인 테이블은 게이트가
  `valid_from <= as_of` 다. 지금은 `sectors` 하나뿐이다. 업종 분류는 준정적이고 수익률
  예측 정보가 아니라서, "2026-08-15 에 처음 받았다" 는 이유로 2025 년 백테스트가
  종목의 업종을 모르는 척하는 것은 미래 훔쳐보기 방지가 아니라 검증 불능이다
  (portfolio-construction.md §7). `observed_at` 은 그대로 진실로 남긴다 — 과거로
  내리지 않는다. 시세·재무·신호·수급처럼 **그 자체가 예측 정보인 테이블에는 절대 켜지
  않는다**; 켜는 순간 그 테이블의 백테스트는 거짓이 된다. 켜는 곳은 스키마 선언 한
  곳이고 백테스트 분기가 아니다(불변식 5).
- **Parquet 직접 읽기·DuckDB 직접 쿼리 금지.** CI에서 검사

에이전트 15개가 각자 데이터를 긁으면 그중 하나는 반드시 미래를 본다.
출입구를 하나로 막는 것이 유일한 해법이다.

## 4. 소스별 함정

| 소스 | 함정 | 처리 |
|---|---|---|
| 가격 | 수정주가에 미래 분할·증자가 반영됨 | 원주가 + **발효일 배율**(`prices.adj_factor`), 읽을 때 접는다 — §4-1 |
| DART 재무 | 회계기간 종료일 ≠ 공시일. 정정공시 존재 | 공시일 기준, 원본·정정본 모두 보관 |
| 뉴스 | 기사 발행시각이 사후 수정됨 | 크롤링 시각을 `observed_at` 으로 |
| SNS | 삭제된 글이 백필에서 사라짐(생존편향) | 수집 즉시 스냅샷 고정 |
| 수급 | 장중 잠정치가 마감 후 정정, 공매도 T+1~2 | 잠정/확정 별도 행 |
| 유니버스 | 상폐 종목 누락 = 수익률 뻥튀기 | 매 거래일 상장종목 명단 스냅샷 |
| **미장 가격(LS)** | **상폐 종목 과거 시세를 아예 안 준다** | 피할 수 없다. 아래 참조 |
| FRED | `/releases/dates` 는 **다가올 날짜만** 준다 | 지난 발표는 `/release/dates` 로 릴리스별 조회 |
| KOSIS | `format=json` 인데 따옴표 없는 키, content-type 은 `text/html` | 키에만 따옴표를 씌워 파싱 |
| ECOS | **무효한 키에 503 HTML 을 HTTP 404 로** 돌려준다 | 응답이 `<` 로 시작하면 서버가 아니라 **키를 의심** |
| SEC `companyconcept` | 사실이 있는 CIK 에도 **200 + 빈 `units`** 를 준다 (HCA·POOL·VFC 실측) | 쓰지 않는다. `companyfacts` 벌크가 진실 |
| SEC 발행주식수 | 기준일(`end`)과 공시일(`filed`)이 30~90일 벌어진다 | `valid_from=end`, `observed_at=filed`. 섞으면 분기마다 미래를 본다 |
| SEC 20-F·6-K | **원주 수**를 신고하는데 미국 시세는 **ADR 한 장** 값이다 | 그 서식의 주식수는 버린다. ADR 비율을 무료로 못 구한다 |
| KRX 지수 | 통합 경로(`/idx/krx_dd_trd`)에 **코스피·코스닥이 없다** | 대표지수는 `/idx/{kospi,kosdaq}_dd_trd` 에 따로 있다 |
| KRX 업종지수 | '화학'·'제조'·'건설'이 코스피에도 코스닥에도 있다 | 이름만으로 `KR:IDX:{이름}` 을 만들면 두 지수가 한 entity_id 로 합쳐진다. (이름, 소속) 쌍으로 고른다 |

**지수는 전부 가격지수(PR)다.** KRX·LS·FRED 셋 다 배당을 반영한 총수익지수를
주지 않는다(유료 라이선스, 실측). 벤치마크로 쓰면 배당수익률만큼(국내 대형주
연 2~3%p) **우리에게 유리하게** 나온다 — 화면·설정·컬럼 설명에 그 사실을 적어
둔다.

**소스 ID 를 짐작하지 않는다.** FRED `release_id` 18 을 소매판매로 짐작해
넣었더니 실제로는 H.15 금리였고, 화면에 "소매판매" 라는 이름으로 금리 일정이
떴다. 새 지표를 넣을 때는 반드시 이름으로 대조한다.

**결측 처리: forward-fill만 허용. backward-fill 절대 금지.**

### 4-0. 미장 재무 — SEC companyfacts (2026-08-29)

`tools/backfill_fundamentals_us.py` 가 `fundamentals(market=US, source=edgar)` 를 채운다. 국장(DART)과
**같은 metric 이름·같은 분기 규약**이다: Q1~Q3 는 3개월 값, Q4 는 연간(10-K) 누적 — Analyst 의
`to_quarterly` 가 그대로 돈다. `fiscal_period` 는 회사 회계연도(`fy`·`fp`) 기준이라 9월 결산사도
회사 안에서는 일관되다. `valid_from` = 회계기간 말, `observed_at` = 접수일 + 18:00 ET.

함정: (1) 같은 (지표, 기간)이 비교 표시·정정으로 여러 공시에 나온다 — **가장 먼저 접수된 것**만
적는다(시장이 처음 안 값, 자연키 중복 회피). (2) 매출 태그가 회사마다 다르다(Revenues /
RevenueFromContractWithCustomerExcludingAssessedTax / SalesRevenueNet 순). (3) 총부채 태그가 없는
회사는 자산 − 자본으로 만든다. (4) USD 단위만 — 시총(market_stats)도 USD 라 earnings_yield 가 선다.
(5) ADR·외국 발행사(20-F/40-F)는 10-Q/10-K 가 없어 빠진다 — 커버리지는 우리 유니버스의 85% 안팎.

### 4-1. 기업행위 — 원주가를 저장하고 읽을 때 접는다

창고에 드는 것은 **원주가**다. 수정주가에는 미래의 분할이 이미 섞여 있어서,
그것을 과거 시점 데이터로 저장하면 백테스트가 아직 일어나지 않은 분할을 안다.

짝이 되는 조정계수를 아무도 채우지 않아 `adj_factor` 가 전 행 `None` 이었고,
그래서 액면분할·무상증자·감자·주식병합이 **가격 급변으로 남아 있었다.**
모멘텀 창이 250일이면 사건 하나가 그 뒤 250세션을 오염시킨다. 5년 국장에서
기업행위 공시가 있었던 종목이 **910개(유니버스의 28%)** 다.

**급락 감시로는 못 찾는다.** 5% 무상증자는 가격이 5% 내려갈 뿐이다. 반대로
급락은 대개 기업행위가 아니다 — 2026년 국장 급락(-60% 미만) 60건을 전수
조회했더니 진짜 기업행위는 21종목이고 나머지는 상장폐지와 **거래정지 후
정리매매**였다(60건 중 50건이 직전일 거래량 0). 그건 **실제 가격**이라 보정
대상이 아니다.

#### 무엇을 저장하나 — 누적이 아니라 **그 세션의 배율**

```
prices.adj_factor(D) = f(D)      그 세션에 발효한 배율. 사건 없는 날은 null
조정종가(t | as_of)  = close(t) × Π f(D)    for  t < D ≤ as_of
```

**누적계수를 저장하면 안 된다.** 누적은 "오늘" 기준이라 저장하는 순간 as_of
마다 틀린다 — 오늘 계산한 0.02 를 2017년 행에 적으면 그 행이 미래를 담는다.

`valid_from` 은 발효일, `observed_at` 은 **그 세션 원본 행의 관측시각 그대로**
다. 조정 기준가는 발효일 아침에 거래소가 공표하므로, 그날 종가를 알 수 있었던
시각이면 배율도 알 수 있었다. 그래서 **분할을 알기 전 as_of 조회가 보정값을
못 보는 것은 게이트가 보장한다** — 읽는 쪽이 조심할 필요가 없다.

과거 구간은 정정본(`revision+1`)으로 넣는다. 값 컬럼을 전부 다시 쓴다 —
게이트가 자연키마다 최신 revision 하나만 고르므로 빈칸을 두면 그 세션 시세가
통째로 null 이 된다.

#### 소스 — LS 가 배율을 직접 준다 (실측 2026-08-15)

`t8410`(국장, 경로는 **`/stock/chart`**) · `g3204`(미장)를 `sujung="Y"`/`"N"`
두 번 불러 나눈 값이 누적 조정계수다. 그 계단이 발효일이고, 계단 양쪽 평탄부의
**중앙값**끼리 나눈 것이 배율이다(KRX 정수 가격 때문에 비율이 ±0.05% 흔들려서,
이웃 두 점을 나누면 그 오차가 그대로 배율에 실린다).

```
삼성전자 2018-05-04 액면분할  0.020000 (1/50)     NVDA 2024-06-10  0.100000
AAPL     2020-08-31  4:1 분할 0.250000            KR:025560 감자   ×17.428571
```

**현금배당은 보정하지 않는다** — 삼성전자·기업은행·하나금융지주 5년 실측에서
사건 0건이다. 보정했다면 우리 가격만 총수익이 되고 벤치마크는 가격지수라
(§벤치마크) 그 차이가 통째로 가짜 알파가 됐을 것이다.

#### 읽는 쪽 — 기본값은 원주가다

`read_prices(..., adjusted=True)` 를 **수익률·변동성·상관을 만드는 쪽만** 켠다.
실제 주문은 원주가로 나가야 하고, 분할 직후에는 주문 게이트(5일)·NAV(30일)
창 안에 사건이 들어와 **주문 수량이 배율만큼 틀어진다.**

한 함수가 두 축을 다 쓰는 자리가 있다(`session/daily.py`·`backtest/market.py`
·`tools/measure_slippage.py`) — 가격·체결가는 원주가, 변동성은 보정가다.
프레임을 두 번 읽지 않고 `store.prices.adjust()` 로 한 번 더 접어 가른다.

사람이 기억할 일이 아니라 `tools/invariant_guard.py` 의 **`price-adjust`**
규칙이 지킨다: 시세를 읽는 파일이 `pct_change` 를 쓰는데 보정을 한 번도 안
켰으면 위반이다.

## 5. 지연 예산

관측 즉시 사용하지 않는다. 실제 파이프라인 지연을 백테스트에 반영한다.

- 파이프라인 각 단계에 타임스탬프를 찍어 실제 소요시간을 기록한다
- 백테스트 지연은 **실측 분포의 p90** 을 사용한다
- 초기값은 넉넉하게 5분에서 시작하고, 파이프라인이 실제로 빨라진 만큼만 줄인다
- 목표는 1분 이내이지만 그것은 **목표이지 가정이 아니다**

LLM 호출이 끼는 경로는 1분 안에 끝나기 어렵다.
가정한 지연과 실제 지연의 차이가 백테스트를 거짓말로 만드는 대표적 원인이다.

## 5-1. 0행의 판정 — "원본이 안 냄" 과 "우리가 못 받음"

수집이 0행으로 끝났을 때 그것이 무엇인지 구분되지 않았다.

| | 뜻 | 예 | 판정 |
|---|---|---|---|
| (가) | 원본이 그날 값을 안 냈다 | 휴장·미공표·그 종목엔 그 사실이 없음 | 정상 |
| (나) | 원본은 냈는데 우리가 못 받았다 | API 오류·인증 실패·타임아웃·파싱 실패 | **실패** |
| (다) | 받았는데 조건에 맞는 행이 없다 | 명단 밖 지수, 시험 실행의 종목 제한 | 정상 |

셋이 전부 "0행" 으로 끝나고 rc=0 으로 나갔다. 그래서 **(나)가 며칠씩 조용히
이어져도 아무도 몰랐다** — `logs/refresh-202608.log` 는 `market_stats=0` ·
`indices=0` 을 "완료 — 실패 0건" 으로 적었고, 2026-08-22 아침 브리핑은 FRED
지수 8/21 을 못 받고도 "적재 140행" 이었다.

### 규칙 셋

1. **창고에 남는다.** `ingest_outcomes` 표에 1행 = 한 데이터셋 · 한 세션 ·
   한 판정. 로그 문구만 바꾸면 사람이 로그를 안 볼 때 판정할 방법이 없고,
   `analyst_failures` 를 만든 것과 같은 이유다 — 나중에 다른 표에서 추론하면
   늦고 그 추론은 정정 한 번에 무너진다. **행이 들어온 세션은 안 적는다.**
   그건 데이터 표 자체가 증거다.
2. **(나)는 rc≠0 으로 나간다.** (가)·(다)는 정상이다. 선례는 커밋 `7ad5680`
   (Analyst 가 죽으면 rc 로 나간다). 셸이 `echo rc=$?` 로 rc 를 삼키던 자리도
   함께 고친다(`scripts/refresh_before_briefing.sh`).
3. **모르면 (나)로 본다.** "휴장이겠거니" 가 조용한 실패를 만든다.

### 빈 응답을 (가)로 부를 수 있는 조건

200 을 받고 0건이라는 사실만으로는 (가)가 증명되지 않는다 — 죽은 키가 빈
블록을 주는 일이 실제로 있다. 그래서 **원본이 이미 냈어야 할 시각인지**를
묻는다. `config` 의 `collectors.available_after_hours.<소스>.<데이터셋>` 이
"원본이 그 세션 값을 낸다고 **실측으로 확인한**" 시각(마감 뒤 시간)이다.

- 공표 시각 전 → `not_published` (기존 `NotYetPublished`)
- 확인된 가용 시각 전 → `too_early` — 실패가 아니라 "나중에 다시"
- 그 시각이 지났는데 0건, **또는 그 시각을 우리가 모름** →
  `empty_unconfirmed` → 실패

설정에 없는 데이터셋은 "확인 못 했다" 이고, 그러면 0건이 실패로 나간다.
**짐작한 값을 채워 넣지 않는다** — 짐작이 들어가는 순간 그 값이 확인한 사실인
척하고 조용한 실패가 다시 시작된다(`publication.UnverifiedSchedulePolicy` 가
같은 이유로 존재한다).

달력이 모르는 유령 휴장일(2026-07-17)은 사람이 `market_hours._OVERRIDES` 에
적어 확인하는 자리다. 확인하면 그날은 애초에 호출되지 않는다. 코드가 알아서
휴장으로 넘겨주는 편의는 두지 않는다 — 그 편의가 수집 실패를 휴장으로
세탁하고 커버리지를 영원히 100% 로 보이게 한다.

### 지금 적용된 곳 / 남은 곳에 적용하는 길

적용: `PanelBackfiller`(KRX Open API 4종 + pykrx 패널 4종), FRED
`IndexCollector`. 계기가 된 두 사건이 각각 이 둘이다.

남은 수집기(`dart_source` · `edgar_filings` · `finra_short` · `kosis_source` ·
`ls_flow` · `ls_us_source` · `thirteen_f` · `us_shares` …)에 같은 방식을
적용하는 길은 셋이다.

1. 0행으로 끝나는 자리마다 `collectors/outcome.py` 의 `record()` 를 부른다.
   판정은 `judge_empty()` 가 준다 — 새 어휘를 만들지 않는다.
2. 실패 판정(`Verdict.ours`)을 호출부의 실패 카운터에 넣는다. 이미
   `BackfillReport.failures` 가 rc 로 나가므로, 그 자리에 얹으면 된다.
3. 그 소스의 가용 시각을 **실측으로 확인해** config 에 적는다. 확인 전까지
   0건은 실패로 나간다. 그것이 의도다.

다음으로 볼 것: `filtered_empty` 가 며칠씩 이어지는 상태. 그건 (다)가 아니라
정규화가 깨진 것이다(`ISU_CD` 를 ISIN 으로 읽어 전 행을 버린 적이 있다).
지금은 판정만 남기고 경보하지 않는다.

## 6. 데이터 범위

- **기간**: 과거 5년 (코로나 급락, 2022 약세장, 회복장 포함 — 레짐 다양성)
- **종목**: 전종목. **상장폐지된 종목까지 포함**해야 생존편향이 사라진다

### 백필 — 관측시각과 소스

과거 데이터를 오늘 내려받을 때 `observed_at` 을 **오늘**로 찍으면 5년치 전부가
"오늘 알았다"가 되어 과거 조회에서 통째로 사라진다. 봉의 날짜로 찍으면 그날
자정부터 종가를 알고 있던 것이 되어 전 구간이 미래를 본다.

**백필의 `observed_at` 은 원 공표 시각이다** — 세션 종료 지역시각 + 공표 지연.
지연은 `store.config` 의 `backfill.{kr,us}_publication_lag_seconds` 에서 읽는다.
라이브 수집은 실제 수신 시각을 쓴다. 코드는 한 벌이고 정책 객체만 갈아 낀다
(`collectors/publication.py`) — `if backfill:` 분기를 만들지 않는다.

소스도 갈린다.

| | 라이브 | 백필 |
|---|---|---|
| 소스 | LS API (`t8410`/`t8436`) | KRX 정보데이터시스템 (pykrx) |
| 축 | 종목당 호출 | **거래일당 호출** |
| 상폐 종목 | 조회 불가 (마스터에 없음) | 그날 명단이라 포함됨 |

날짜 축으로 도는 것이 핵심이다. 종목 축으로 돌면 "오늘 존재하는 종목 목록"에서
출발하게 되고, 그 순간 생존편향이 데이터에 새겨진다.

> KRX 는 2025년부터 `data.krx.co.kr` 로그인을 요구한다 (`KRX_ID`/`KRX_PW`).
> 자격증명이 없으면 pykrx 는 예외가 아니라 **빈 결과**를 돌려준다 — 조용한 실패라
> 수집자 쪽에서 빈 응답을 명시적으로 거부한다.
>
> 네이버 계열 무료 소스는 쓰지 않는다. 수정주가만 준다 — 2021-04-08 카카오 종가를
> 109,992(실제 548,000)로 돌려준다. 일주일 뒤 액면분할이 소급 반영된 값이다.

상장폐지는 별도 소스로 받지 않고 **스냅샷 차분으로 유도한다**. 어제 명단에 있고
오늘 없으면 그것이 상폐다. 행을 지우는 대신 `is_listed=False` 인 새 행을 남긴다.

### 미장의 생존편향 — 피할 수 없고, 숨기지 않는다

국장 백필은 **세션 축**이다. KRX 가 날짜 축으로 전종목을 주므로 그날 상장돼
있던 종목이 자동으로 다 잡히고, 지금은 상장폐지된 종목까지 들어온다.

**미장은 종목 축일 수밖에 없다.** LS 해외주식(g3204)은 심볼 하나의 전 기간을
주므로 세션 축으로 돌면 600종목 × 1,500세션 = 90만 호출이 되어 끝나지 않는다.
그리고 종목 축은 "오늘 존재하는 목록" 에서 출발한다.

유니버스를 완벽히 복원해도 해결되지 않는다. **LS 가 상폐 종목의 과거 시세를
주지 않기 때문이다** — 실측(2026-08-13):

| 종목 | 결과 |
|---|---|
| AAPL (대조군) | 21행 ✅ |
| ATVI (MS 인수, 2023-10 상폐) | **0행** |
| TWTR · SIVB · FRC | **0행** |

즉 생존편향은 유니버스가 아니라 **가격 소스 쪽 제약**이다.
**이 소스로 잰 미장 IC 는 부풀려진 값이다.** 6년이면 출발 유니버스의 20~30%가
사라지고 사라진 쪽은 대체로 성적이 나빴다.

숨기지 않고 갖고 간다 — 저장되는 행의 `source` 가 `ls_us` 이므로 어느 데이터가
이 제약 아래 있는지 창고에서 바로 구분된다. 해소하려면 delisted 를 포함하는
유료 소스(Polygon/Sharadar 등)로 갈아 끼워야 한다.

### 미장 시가총액 — 곱셈의 두 항이 다른 속도로 온다

`market_cap = 주가 × 상장주식수` 인데 **미장은 두 항의 소스가 다르다.** 국장은
KRX 일별매매가 시세와 같은 콜에서 `LIST_SHRS`·`MKTCAP` 을 주지만, 미장은
시세(LS g3204)도 종목마스터(g3101)도 발행주식수를 주지 않는다 — 실측으로
확인했다. 그래서 SEC EDGAR `companyfacts` 벌크(1.4GB, 무료, 키 불필요)에서
따로 받아 곱한다 (`collectors/us_shares.py`).

주가는 매일, 발행주식수는 **분기에 한 번** 바뀐다. 그래서 그날 시가총액은
"그날 종가 × **그날까지 알려진 마지막** 주식수" 다.

| 행 | valid_from | observed_at |
|---|---|---|
| `shares` | 공시 표지의 기준일(`end`) | **공시일(`filed`)** + EDGAR 접수 마감(18시 ET) |
| `market_cap` | 세션 | 그 세션 **봉의 관측시각** |

`end` 로 관측시각을 찍고 싶어지지만 그러면 안 된다 — 둘은 30~90일 벌어지고
(AAPL: end 2026-07-17, filed 2026-07-31), 그 사이 아무도 모르는 숫자를 알고
있는 것이 된다. 어느 주식수가 "그날까지 알려진" 것인지는 봉의 관측시각으로
자른다.

**ADR 은 곱하면 안 된다.** 20-F·6-K 를 내는 외국 발행인은 SEC 에 *원주*
수를 신고하는데 미국 시세는 *ADR 한 장* 값이다. 1 ADR = N 원주라 그냥 곱하면
ADR 비율만큼 틀린다. 서식별로 재 본 결과(2026-08-15 실측, 시가총액 상위):

| 주력 서식 | 종목 | 최대 시총 | 판정 |
|---|---|---|---|
| 10-Q·10-K | 4,316 | NVDA 5,423B$ | ✅ 정상 |
| **20-F** | 907 | **LTM 30,112B$** · TSM 11,129B$ | ❌ 원주 기준. 버린다 |
| **6-K** | 8 | GLDI 657B$ (ETN) | ❌ 버린다 |
| 40-F (캐나다) | 149 | RY 299B$ · TD 208B$ | ✅ 보통주 직상장. 남긴다 |

ADR 비율은 무료로 신뢰성 있게 못 구한다. **그래서 채우지 않는다** — 틀린
시가총액은 없는 것보다 나쁘다. 리더·트리맵이 그 거짓을 맨 위에 올리고,
밸류 팩터는 그 종목을 영원히 초저평가로 읽는다.

커버리지는 **6,648종목 중 4,502개(68%)** 다 (2026-08-15 실측). 빠지는 쪽은
ADR(20-F) 907개, ETF·폐쇄형 펀드·워런트(발행주식수 태그가 없다), 그리고
티커가 CIK 를 갈아탄 종목이다. **모르는 종목은 행을 만들지 않는다** — 0 을
넣으면 "시가총액 0" 이라는 다른 사실이 되어 리더·트리맵 정렬이 그 거짓을 읽는다.

갱신은 **주 1회**다. 분기 공시지만 회사마다 결산월이 달라 새 공시가 매주
들어오므로, 분기 1회로 잡으면 최대 석 달 묵은 주식수를 쓰게 된다.

### 데이터 유니버스 ≠ 매매 유니버스

전종목을 모으되, 실제로 살 수 있는 종목만 후보로 올린다.

매매 유니버스 필터:
- 최근 20일 평균 거래대금 하한
- 관리종목·거래정지 제외
- 상장 후 6개월 경과
- 1주 가격이 자본의 15% 미만 (소액 구간에서 특히 중요)

## 7. 리플레이 엔진

### Clock 추상화

```python
class Clock:
    def now(self) -> datetime: ...

LiveClock()            # 실제 시각
ReplayClock(as_of)     # 지정된 과거 시각
```

`datetime.now()` 직접 호출 전면 금지. CI에서 grep으로 검사한다.
백테스트와 라이브는 **같은 워커 코드**를 쓰고 Clock만 바꿔 낀다.

### 에이전트 출력 캐시

```
(agent, agent_version, entity_id, as_of, features_hash) → output
```

영구 저장. 리플레이 시 LLM 재호출 없음.
이것이 리플레이 결정론과 LLM 비용 문제를 동시에 해결한다.

### 이벤트 로그

```
{run_id, seq, ts_wall, ts_sim, stage, actor, payload_hash, payload}
```

관측 → Signal → Selector 결정 → Allocator 액션 → 주문 → 체결까지 전 단계 append-only.
리플레이는 이 로그를 재생한다.

```
충격비용 = k × 변동성 × √(주문량 / 일평균거래량)
```

슬리피지를 고정값으로 두면 소형주 수익률이 뻥튀기된다.

정수 라운딩, 최소 주문금액.
