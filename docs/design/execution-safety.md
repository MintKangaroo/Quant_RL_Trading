# Execution safety contract — 2026-09-09

감사 기준: [플랫폼 감사](../quant-platform-audit-2026-09-09.md). 기존 계획·분할·브로커·체결 대사를 유지하면서 전송 경계를 보강한다.

1. **계획 시각과 실행 시각을 구분한다.** 주문의 자연키와 `valid_from`은 계획을 가리킨다. 매번 전송하기 직전 주입된 `Clock.now()`로 kill latch, 최신 일봉의 기대 거래 세션, 회로 차단을 다시 검사한다. 검사 결과는 주문과 함께 기록한다. 매도는 기존 청산 허용 정책을 유지한다. 위험 승인이 없는 매수 재호가는 금지하고 확인된 잔량의 취소를 요청한다.
2. **동시 전송도 한 번만 시도한다.** Store의 `(table, ingest_run_id)` 적재를 로컬 파일 잠금으로 직렬화하고, 주문 전송 claim을 영속화한 호출만 브로커를 부른다. 프로세스가 중단되면 잠금은 해제되지만 claim은 유지된다. claim 기록이 불완전하면 자동 재주문하지 않는다. Linux/POSIX 로컬 파일시스템 범위의 보장이다. 여러 호스트·서로 다른 저장 루트가 같은 계좌에 주문하려면 공유 트랜잭션 저장소가 별도로 필요하다.
3. **브로커 어댑터도 요청 전체를 잠근다.** 같은 ID에 대한 성공 결과를 재사용한다. 전송 결과가 불확실한 ID는 어댑터 수명 동안 재전송하지 않는다. 확정 거부와 미전송 paper 응답은 구분한다.
4. **취소 요청은 취소 완료가 아니다.** 접수 ACK만 있거나 응답이 없으면 `cancel_unknown` 또는 `modify_unknown`으로 남긴다. 부분체결은 반영하되 불확실한 주문을 자동 정정·취소하지 않는다. 체결 대사에서 전량 체결을 확인하면 `filled`로 종결할 수 있다. 브로커의 취소 확인 자료가 없으면 운영자가 대사해야 한다.
5. **일봉 freshness는 경과 시간만으로 판정하지 않는다.** 거래소 달력·시간대와 장 마감 및 설정된 수집 지연으로 기대 완료 세션을 계산한다. 주말·휴일은 건너뛰고, 장중에는 직전 완료 세션까지 요구한다. 주문 종목별로 검사한다. 일봉 freshness는 실시간 호가 freshness를 대신하지 않는다.

`loop.run → daily.run → pipeline.run`에 `execution_clock`을 주입한다. `run_session --live-broker`는 이 경계에 `LiveClock`을 전달하고, 일반 재생은 기존 세션 시계를 사용한다. signal의 `as_of`와 자연키를 오늘 날짜로 바꾸지 않는다. 주문 응답이 불확실하면 kill latch를 걸어 후속 신규매수도 차단한다. 미확정 주문의 체결을 확인한 뒤 수동으로 해제한다.

초기 패치의 신규 전송 claim에 이어, 아래 취소·정정 저널이 장중 조치의 영속 intent와 KR 확인 이벤트를 연결한다. 누락 이벤트와 과거 주문의 날짜 지정 대사는 계속 후속 범위다.

회귀 검증은 임시 Store와 가짜 브로커만 사용한다. 실제 계좌에 주문하지 않는다.

## 계좌 예산 계약 — 후속 구현

- `risk` 계층은 회계의 Book/NAV/결제 완료 현금과 주문 저널에서 예산을 구성한다. NAV는 재계산식을 만들지 않고 `accounting.snapshot`을 사용한다. 통화별 현금은 별도로 제한하고 KR·US 명목 노출은 원화로 환산해 합친다.
- 매수 예약은 **미체결 수량 × 허용 최대 지정가 + 수수료**다. 기존 chase가 원 지정가에서 추가로 `execution.max_slippage`까지 정정할 수 있으므로 그 상한까지 예약한다. 보유 평가액과 미체결 매수 예약을 합쳐 종목 비중·총 노출·동시 보유 수를 제한한다. 미체결 매도대금은 매수 예산이 아니다. 매도도 이미 예약된 매도 잔량을 빼고 검사해 보유보다 많이 팔 수 없다.
- 주문 계획은 승인 전 `planned`, 예산 승인 후 `reserved`다. 분할 주문 전체를 먼저 예약하고, 각 조각을 전송하기 직전 최신 위험 상태로 다시 검사한다. 승인되지 않은 `planned`는 백테스트에서 체결시키지 않는다.
- `reserved/paper/submitting/sent` 및 취소·정정 미확정 잔량은 예약을 유지한다. 과거 `cancelled/expired/abandoned/filled` 표기만으로 실제 브로커 주문의 잔량을 해제하지 않는다. 장부의 전량 체결 또는 별도의 명시적 최종 취소 확인이 필요하다. 경과 일수로 UNKNOWN을 성공·만료로 바꾸지 않는다.
- 같은 Store 루트의 계좌 잠금 안에서 예약 검사·상태 적재·전송을 처리한다. 체결 장부 갱신과 주문 감독도 같은 잠금을 사용한다. 스레드 재진입을 허용하고 프로세스간에는 POSIX 파일 잠금을 쓴다. 서로 다른 루트/호스트가 같은 실제 계좌를 공유하는 구성은 이 잠금의 보장 범위가 아니다.
- 시뮬레이터는 예약 승인된 주문만 다음 세션에 체결하고 해당 시도 종료를 `simulated`로 기록한다. 잔여 수량의 day-order 만료는 시뮬레이터가 확정할 수 있다. `simulated`는 동일 구간 재생에는 사용할 수 있지만 예산 예약에는 포함하지 않는다.
- 신규 한도는 config에 명시한다. 일 손실은 기존 회계의 서울 세션 기준 TWR, MDD는 TWR 누적지수 기준이다. 위험 데이터·현금·평가를 확정할 수 없으면 매수를 승인하지 않는다. 전략별 원장 식별자가 없는 현행 구조에서는 전체 계좌 예산까지만 보장하고 전략별 예산을 지어내지 않는다.

이 예산 검사는 가격·체결 모델의 수익성을 검증하지 않는다. 취소/정정의 확인 증거는 아래 조치 저널 계약을 따른다.

체결 대사는 조회 범위 밖의 과거 주문번호를 당일 주문번호와 매칭하지 않고
UNKNOWN으로 유지한다. 과거 주문일을 지정하는 브로커 대사는 후속 작업이며,
새 KR 취소 확정 이벤트의 영구 기록은 아래에 연결했다. 현재 취소 접수 응답만으로 예약을 해제하지 않는다.

계좌 일일 손실과 평가 구간의 시작 지수는 accounting의 `previous_session_snapshot`
기준을 공유한다. 같은 서울 날짜에 기록된 장중 snapshot은 전일 기준을 대체하지 않는다.
주문가능 현금의 결제일 계산은 해당 시장의 현지 날짜와 거래일 캘린더를 사용한다.
UTC 날짜가 먼저 바뀌었다는 이유로 다음 미국 거래일의 매도대금을 미리 풀지 않는다.
결제 지연 일수는 기존 설정을 그대로 적용하며 브로커별 실제 결제 규칙 확정은 별도다.
장 마감의 명시적 close에서는 전송 claim이 없는 planned/reserved 조각만 withdrawn으로
기록해 예약을 해제한다. submitting/sent/UNKNOWN 및 브로커 주문번호가 있는 행은
이 경로로 해제할 수 없다. 뒤늦은 release 호출은 withdrawn 행을 재전송하지 않는다.

예약 승인과 모의체결 권한은 다르다. `reserved` 중 PaperBroker에 귀속된 계획만
`reason=simulation_only`로 표시한다. 모의체결기는 이 표시가 있는 예약과 paper ACK만
새로 체결한다. 실제 브로커용 미전송 reserved는 모의체결하지 않는다. simulation_only
예약을 나중에 실제 브로커로 전송하는 모드 변경도 차단한다.

## 취소·정정 조치 저널과 확인 증거

다음 변경은 신규 주문 저널을 보존하면서 `execution_events` append-only 테이블을
추가한다. 신규 브로커 접수의 실제 주문일·원번호·자격증명 지문, 취소/정정 intent,
접수 응답, 거래소 확인을 서로 다른 사건으로 기록한다. 계좌번호·토큰·원본 계좌
잔고를 저널에 복사하지 않는다. 모든 사건은 Clock 관측시각과 결정론적 event ID를 가진다.

1. 조치는 같은 계좌 잠금 안에서 **intent 적재 → API 호출 → ACK 적재** 순서다.
   intent만 있거나 ACK만 있으면 재시작 뒤에도 UNKNOWN이다. 자동 재전송하지 않는다.
   복구 시 원 기준가·현재 확인된 가격·주문번호·재시도 횟수·마지막 조치시각을 복원한다.
2. 취소/정정 접수 ACK는 거래소 확인이 아니다. 감독기는 ACK 성공이어도 UNKNOWN을
   유지한다. 확정 거부는 별도 기록하며, 확인 전에는 다음 조치를 시도하지 않는다.
3. KR 최종 확인은 인증된 LS 계좌 실시간 SC2/SC3 수신 경로에 연결한다. 계좌 지문,
   실제 주문일, 종목·방향, 원주문번호, 조치 intent와 확인 수량/가격을 대조한다.
   SC3 `canccnfqty`로 입증한 취소 수량만 예약에서 차감한다. 미기록 체결은 해제하지 않는다.
   접수 ACK·주문 조회 누락·`ordrem=0`만으로 취소를 확정하지 않는다.
4. 같은 취소번호 확인을 중복 합산하지 않는다. 상충된 확인이나 수량 초과는 거절한다.
   체결과 취소를 합쳐 원수량을 소진했을 때만 취소 완료 상태로 본다.
5. 실시간 수신 끊김/날짜 변경/누락은 취소 증거가 아니다. 미확정 예약은 남긴다.
   수신 도구는 주문을 제출하지 않으며 현재 변경에서는 자동 기동·운영 배포하지 않는다.
   기존 주문일/계좌 지문을 증명할 수 없는 legacy 주문과 US 최종 취소는 계속 미확정이다.

공식 근거(2026-09-09 공개 문서 읽기):
- [LS 계좌 API](https://openapi.ls-sec.co.kr/apiservice?api_id=37d22d4d-83cd-40a4-a375-81b010a4a627): t0425 확인수량은 취소 전용 필드로 선언돼 있지 않다. CSPAQ13700에는 OrdDt·정정취소 구분/수량이 있지만 상태 코드별 최종성까지 문서에서 확인하지 못했다. 이를 취소 확정으로 추정하지 않는다.
- [LS 계좌 실시간](https://openapi.ls-sec.co.kr/apiservice?api_id=9a2800c3-9bf2-4d67-8d83-905074f06646): SC2는 정정확인수량/가격, SC3는 취소확인수량과 원주문번호를 제공한다. 공개 `/api/apis/guide/tr/property/{trId}` 필드표와 예제를 대조했다. 브로커 실계좌에서 검증한 것은 아니다.

회귀 조건: ACK만으로 종결 금지, 호출 직후 프로세스 중단/재시작 시 재전송 금지,
다른 프로세스의 오래된 상태 재사용 금지, 확인 전 예약 유지, 부분체결+부분취소,
중복/상충/타계좌/다른 주문일/다른 종목 확인 거절, 정정 확인 후 새 번호·재시도 복원.

확인 이벤트가 도착하면 해당 주문의 상태만 저널에서 재구축한다. 증거 적재 뒤 상태 투영이
중단돼도 다음 수신·체결 대사·chase 실행에서 회복할 수 있다. 예약은 상태 문자열 대신
실제 체결·확인된 취소 수량을 직접 읽는다. 원 주문 행의 수량·지정가·브로커 원번호는
보존하고, 현재 정정 번호·가격은 조치 저널에서 복원한다.

부분체결 대사의 금융 계약: 누적수량 `Q`, 누적 평균가 `P`, 기록된 수량 `q`,
기록된 거래대금 `N`일 때 신규 체결은 `(Q-q)`주, 대금은 `Q×P-N`, 단가는
`(Q×P-N)/(Q-q)`다. 누적 평균가를 신규 수량에 그대로 적용하지 않는다.
`Q + confirmed_cancelled ≤ original_quantity`를 검사하고 수량 역행·비정수·비유한값,
양수가 아닌 신규 대금은 UNKNOWN이다. 누적 가격의 정밀도와 설정 수수료·세금에 따른
대사이며, 거래소 개별 체결 ID·실제 비용 명세를 대체하지 않는다.

[LS 공식 웹소켓 예제](https://openapi.ls-sec.co.kr/howto-sample)의 `/websocket` 경로,
운영/모의 포트와 계좌 등록 유형을 사용한다. 수신기는 서버 구독 ACK를 확인하고,
지문 불일치·구독 거절·날짜 변경·연결 실패 시 성공으로 종료하지 않는다.
토큰 발급과 실시간 계좌 구독만 하며 주문 API는 호출하지 않는다.

2. **주문일의 출처.** `execution_events` 의 `submitted` 가 있으면 그 `order_day` 만 조회하고

   돌려도 한 행이다. **`valid_from` 은 `OrdDt`+`LastExecTime`(KST) — 체결이 사실이 된 시각이다.**

### 스냅샷 정정과 이중계상 — 이 대사의 가장 위험한 자리 (2026-09-27 실측)

`tools/reconcile_snapshot.py` 는 주문별 대사가 놓친 체결을 **"브로커 보유 − 장부 보유"** 차이로
되찾아 `trades` 에 정정 거래로 넣는다(`source=snapshot_reconcile`,
`order_id=snapshot-recon-<날짜>|<종목>`). 그 행은 **주문번호가 아니라 종목·날짜에 붙는다** —
`risk.account.filled_quantities` 는 그것을 원래 주문의 체결로 세지 못한다. 그래서 주문일 대사가
같은 체결을 "장부에 없다" 로 보고, 적으면 **포지션과 현금이 두 배**가 된다.

모의계좌 실측으로 이건 가설이 아니다. 9/1 정정과 그날 대사 대상이 **수량까지 같다**:
KR:100700 5,703 = 1,901×3 · KR:013580 598 = 200+199+199 · KR:004000 206 = 103+103 ·
KR:001800 18 = 5+5+4+4 · KR:054210 705 · KR:095660 237 · KR:420570 70(8/31).
즉 **지금 창고의 "체결 누락" 37건은 이미 장부에 들어 있다.**

그래서 `backlog.snapshot_corrections` 가 (주문일, 종목) → 정정 수량을 읽고, 그 자리에 정정이
있으면 분류를 `체결·스냅샷중복` 으로 바꿔 **적재를 막는다.** 옮겨 적으려면 정정 거래를 먼저
무효화해야 하고(장부에 `void` 경로가 있다), 그건 같은 변경에 섞지 않는다 — 회계를 건드리는 일이다.
**남는 이득은 분류 자체다**: 어느 체결이 어느 주문의 것인지 알게 되므로, 나중에 정정을 무효화하고
주문별 체결로 갈아 끼우면 슬리피지·집행 측정이 주문 단위로 정확해진다.

**이번 범위에서 하지 않는 것.** 체결이 0 으로 확인된 지난 주문의 잔량을 `expired` 로 종결하는 것은
빼 둔다. 그러려면 "당일 소멸" 을 수량 원장에 적는 새 사건(`expired_confirmed`)이 필요하고, 그 원장은
예약을 계산하는 자리다 — 체결 누락을 찾는 작업과 같은 변경에 섞지 않는다. 조회로 "그날 체결 0" 을
확인한 건수는 보고만 한다. 여는 조건: 체결 대사가 먼저 끝나고, 사람이 잔량 종결 규칙을 승인한 뒤.

     **전부** 조회했고 조회가 성공했다(빈 날 `00707` 은 "0 건" 으로 성공).
   - 그 날들의 같은 종목·같은 방향 행이 **전부 우리 다른 조각의 번호로 설명된다.** "설명된다" = 번호·종목·방향·원주문
     수량이 장부의 어떤 주문(`orders.reason` 의 `broker_order_no` 또는 전송 저널 `submitted`)과 맞고, 저널이 주문일을
     말하면 그 날과도 맞는다. 정정·취소 사슬의 자식 행은 원주문번호(`OrgOrdNo`)가 설명되면 설명된 것으로 본다.
     설명 안 되는 행이 하나라도 있으면 **거부** — 그게 우리 조각일 수 있다(응답만 못 받은 경우). 사람이 LS 화면을 본다.
3. **적는 것:** `orders` 에 그 조각의 새 revision 한 행(append-only). `status = rejected`,
   `reason = "미도착 확인 — …"`(조회한 날·행 수·같은 종목 행과 그 번호가 누구 것인지), `source = not-received-confirmed`,
   `valid_from` 은 원행 그대로, `observed_at` 은 적는 시각. `trades`·NAV·`execution_events` 는 건드리지 않는다.
   `rejected` 는 기존 종결 상태라 예약·대사·추격·대시보드 분류가 이미 안다. `refresh_order_states` 는 사건이 있는 주문만
   되적으므로 사건 0 건인 이 조각을 덮어쓰지 않는다. 새 상태(`not_received`)는 상태를 나열하는 곳이 많아 쓰지 않는다.
4. **`_orphans` 고침.** 번호 없는 건의 "사람 확인용 후보" 에서 위 규칙으로 이미 설명된 행을 뺀다 — §5 문장 그대로("우리
   번호로 설명되지 않는 것"). 9/27 오해가 이것에서 나왔다.
5. **경고 문구·빈도.** `reconcile_fills` 는 실제 상태를 찍고, 지난 거래일 건은 줄마다 찍지 않고 건수 한 줄 + 보기 셋으로 접는다
   (9/17 의 178줄과 같은 처리). 오늘 건은 지금처럼 줄마다 찍는다.

**다시 볼 조건.** 거부가 나면(설명 안 되는 행) 그건 "응답만 못 받은" 진짜 사례다 — 그때 체결을 그 조각에 묶는 절차를 따로
설계한다(지금은 없다, 이중계상 위험 때문에 같은 변경에 섞지 않는다).

## 2026-09-28 E1 집행 계획 계약 — AI 는 세션 전에 적고, 집행기는 읽기만 한다

근거: [AI 풀스택](ai-full-stack.md) §1 ⑥·§2·§5. 등록 초안: `docs/protocols/execution-bandit-2026-10.md`.
노출 부품(`exposure_actions` · `selector.exposure.learned_decision`)과 **같은 계약**이다. 불변식 6(집행기 안에 AI 없음)을 그대로 지킨다.

**바꿀 수 있는 것은 한 줄이다**: 종목 주문 하나의 **조각 수 · 조각 간격**. 지정가 여유(`execution.max_slippage`)·수량·방향·
사이징·예산·게이트·추격(chase)은 계획이 건드리지 못한다 — 구조로 막는다(`SliceParams.max_slippage` 는 언제나 설정값).

1. **표 `execution_plans`** (append-only, `observed_at` 필수). 한 행 = (세션·종목·부품) 하나의 팔.
   `entity_id` = 종목, `valid_from` = `observed_at` = 그 세션 기준 시각(`backtest.loop.snapshot_moment` — 노출 행동과 같은 규약),
   `source` = 부품 이름(예: `e1-bandit`), `arm` = 팔 이름, `propensity` = 그 팔을 고른 확률(무작위화 기록 — 오프폴리시 평가에 필수),
   `detail` = 문맥(JSON, 설명용 — 집행기가 안 읽는다). 자연키 (entity_id, valid_from, source).
   **부품은 한 세션에 한 번만 적는다**(ingest_run_id 에 세션을 넣어 두 번째 적재가 `DuplicateIngestRun` 으로 죽는다) — 세션이 기록한 조각과
   `release_slices` 가 나중에 읽는 계획이 같아야 하기 때문이다.
2. **팔 카탈로그는 코드에 고정**(`executor/plans.py ARMS`) — 등록된 행동 공간이다. 설정에 두면 판정 뒤에 팔이 조용히 바뀐다.
   | 팔 | 조각 | 간격 | 뜻 |
   |---|---|---|---|
   | `4x60` | 4 | 3600초 | **C0** = 지금 규칙(08:40·09:40·10:40·11:40 기준 개장) |
   | `2x30` | 2 | 1800초 | 오전에 빨리 끝낸다 |
   | `1x0` | 1 | 0 | 개장 단일가 한 번(9/1 이전 동작) |
   | `8x30` | 8 | 1800초 | 잘게, 오전~점심까지 |
   `4x60` 은 설정 기본값(`slice_count`·`slice_interval_sec`)과 같아야 한다 — 다르면 C0 가 규칙이 아니게 된다(테스트가 고정).
3. **읽기 경로**(`executor/plans.py`, 순수 코드). `execution.plan_source` 가 `"rule"`(기본·설정에 없을 때도)이면 **표를 읽지도 않는다** —
   지금 실전 동작이 바이트 단위로 그대로다. 부품 이름이면 그 `source` 의 행만, **세션 기준 시각에서 12시간 넘게 낡은 행은 버리고**
   (`ACTION_MAX_AGE` 와 같은 값), 모르는 팔 이름도 버린다. 없거나 버린 종목은 규칙(설정값)으로 물러선다 — 세션 노트에 "계획 n · 규칙 m".
   **시장가 주문(청산·킬스위치)과 청산 전용 세션에는 계획을 적용하지 않는다** — 안전 경로는 규칙만 탄다.
4. **세션과 조각 방출이 같은 계획을 본다.** `pipeline.run` 은 `as_of` 로, `tools/release_slices.py` 는 **그 주문 행의 `valid_from`**(= 세션 `as_of`)으로
   계획을 읽는다. 조각 시각은 종목마다 그 팔의 간격으로 판정한다(`plans.due_slices`). 방출 주기는 20분이라 30분 간격 팔의 실제 방출은 +0~20분 늦다
   (규칙 60분 간격도 같은 성질).
5. **켜는 곳은 샌드박스뿐**(`config-overrides` 로 `execution.plan_source`). 모의계좌·실계좌는 §2.4 사다리(사전등록 판정 → 금고 → shadow → 사용자 승인)를
   다 지난 뒤에만. 기록 단계에서는 부품이 계획을 **적기만** 하고(무작위 팔 = 행동 기록), 집행기는 규칙으로 돈다.

**보상(기록용, 집행기 밖)**: `tools/measure_execution.py --shortfall`. 논리 주문(세션·종목) 하나마다
도착가 = **집행일 시가**(개장 단일가 — 팔이 영향을 줄 수 없는 밤사이 갭을 뺀다), 구현 손실 = Σ 체결수량×(체결가−도착가)×방향 +
미체결수량×(집행일 종가−도착가)×방향(기회비용), bps = ÷(계획수량×도착가). 손해가 양수. 수수료·세금은 팔과 무관한 고정비라 뺀다.
참고로 전 세션 종가 대비와 당일 VWAP 대비(분봉이 있을 때)를 같이 적는다.
