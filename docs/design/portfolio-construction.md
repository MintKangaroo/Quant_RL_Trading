# 포트폴리오 구성 — 섹터 방어 구조

스코어 비례 배분은 **리스크 구조를 완전히 무시한다.**
스코어 상위 20종목이 전부 반도체면 그건 분산이 아니라 한 종목 몰빵이다.

이 문서는 "무엇을 사는가"가 아니라 **"얼마나 사는가"** 를 리스크 구조에서 유도한다.

---

## 1. 방어 관계는 가정하지 말고 측정한다

"통신·유틸은 방어주"는 통념이지 사실이 아니다. 시기에 따라 바뀐다.
2022년 금리 급등기에는 유틸·리츠가 오히려 더 빠졌다.

**하방 베타로 직접 측정한다.**

```
시장이 하락한 날만 골라서:
  downside_beta(sector) = cov(r_sector, r_mkt | r_mkt < 0) / var(r_mkt | r_mkt < 0)
```

| downside_beta | 의미 |
|---|---|
| < 0.7 | 하락장에서 실제로 방어 |
| ≈ 1.0 | 시장과 같이 빠짐 |
| > 1.3 | 하락장에서 더 크게 빠짐 |

**상방 베타도 같이 잰다.** 이상적인 방어 섹터는 `하방 베타 낮고 상방 베타 높은` 비대칭 섹터다.
둘 다 낮으면 그냥 현금과 비슷하고, 그럴 바엔 현금을 드는 게 낫다.

> 상방/하방 베타를 **롤링 250일**로 계속 갱신한다. 고정 테이블로 박아두지 않는다.

---

## 2. 개별 종목 공분산을 직접 추정하지 않는다

30종목이면 상관계수가 435개다. 250일 표본으로 추정하면 **거의 전부 노이즈**다.
그대로 최적화기에 넣으면 추정 오차가 가장 큰 쌍에 극단적 비중이 몰린다
(mean-variance optimizer 의 고전적 실패).

**팩터 모델로 차원을 줄인다.**

```
r_i = α_i + Σ β_i,k · F_k + ε_i

F_k = 시장, 섹터(10개 내외), 시총, 밸류, 모멘텀, 변동성
```

이러면 추정 대상이 435개에서 **팩터 공분산 10~15개 + 종목별 노출**로 줄어든다.
훨씬 안정적이고, 무엇보다 **"이 섹터가 빠지면 저 섹터가 어떻게 되나"가 팩터 공분산에 직접 들어온다.**

여기에 **Ledoit-Wolf shrinkage** 를 걸어 추정 오차를 더 줄인다.

---

## 3. 비중 산출 — 리스크 기여 균등 + 스코어 틸트

순수 mean-variance 는 소액·소수 종목에서 불안정하다. 두 단계로 간다.

### 1단계 — 리스크 기여 기준선

```
RC_i = w_i · (Σw)_i / σ_p        (종목 i 의 포트폴리오 위험 기여도)
```

기준선은 **섹터별 리스크 기여를 균등하게** 만드는 비중이다.
금액이 아니라 **위험**을 균등 배분한다는 게 핵심 — 변동성 큰 반도체와
변동성 작은 통신에 같은 금액을 넣으면 위험은 반도체가 3배다.

### 2단계 — 스코어로 틸트

```
w_i ∝ RC기준선_i × exp(γ · combined_score_i)
```

`γ` 가 공격성이다. 0이면 순수 리스크 패리티, 크면 스코어 비례에 가까워진다.
**γ 는 진화 탐색 대상**으로 둔다 (Selector 유전자에 추가).

### 3단계 — 제약 투영

```
섹터 리스크 기여 상한   35%
단일 종목 리스크 기여   15%
하방 베타 가중평균      1.0 이하
현금 하한               레짐에 따라
```

---

## 4. 위기에는 상관이 1로 수렴한다 ⚠️

**이게 가장 중요한 현실이다.**

평시 상관 0.3이던 섹터들이 폭락장에서는 0.8~0.9로 붙는다.
"반도체가 빠지면 통신이 방어한다"는 관계는 **정작 필요한 순간에 사라진다.**

그래서:

- 공분산은 **하락 국면 표본에서 별도로 추정**해 두 개를 유지한다 (평시 / 위기)
- Regime Analyst 가 위기를 판정하면 **위기 공분산으로 전환**한다
- 위기 공분산에서는 섹터 분산의 방어 효과가 거의 0으로 계산되고,
  최적화기는 자연스럽게 **현금 비중을 올린다**

> 주식 안에서의 섹터 로테이션으로는 위기를 못 막는다.
> 진짜 방어는 **현금**이고, 그다음이 **통화**다.

### 원화 기준 평가의 자연 헤지

우리는 원화 기준으로 성과를 재기로 했다. 원화는 위기에 약해지는 통화이므로
폭락장에서 원달러가 오르고, **미장 포지션이 원화 기준으로 손실을 상쇄한다.**

이건 섹터 로테이션보다 강한 방어 장치다.
Allocator 상태값의 환율·환율변동성이 이 효과를 학습하는 경로다.

---

## 5. Allocator(RL)와의 충돌 처리 ⚠️

여기가 설계상 가장 위험한 지점이다.

RL 이 비중을 정하는데 그 위에 최적화기가 얹히면, **최적화기가 RL 출력을 덮어쓴다.**
그러면 액션 반영률이 떨어지고 — 그게 정확히 선행 프로젝트를 무너뜨린 실패 모드다.

**해결: 최적화기를 뒤가 아니라 앞에 둔다.**

```
❌ RL 비중 → 최적화기가 수정 → 주문
✅ 리스크 모델 → RL 상태값으로 제공 → RL 비중 → 최소 투영 → 주문
```

- Risk Analyst 가 팩터 노출, 하방 베타, 섹터 리스크 기여를 **상태값으로** 제공
- RL 은 제약을 보면서 스스로 만족하는 비중을 낸다
- Executor 는 **위반 시에만 최소 거리 투영**을 한다
- 투영 전후 차이를 **액션 반영률로 측정**하고, 30% 미만이면 경고

M3 룰 베이스라인에서는 §3 최적화기를 그대로 쓴다.
M4 에서 RL 이 이 베이스라인을 못 이기면 RL 을 쓸 이유가 없다는 판정 기준도 그대로다.

---

## 6. 소액 구간의 현실

최적화 결과가 4.2%인데 1주가 7%면 그 최적해는 존재하지 않는다.
종목 5~8개 구간에서는 정교한 최적화가 **정수 라운딩에 파괴된다.**

소액 구간에서 실효적인 것은 세 가지뿐이다:

1. **섹터 상한** (한 섹터 2종목 초과 금지 수준)
2. **하방 베타 가중평균 상한**
3. **현금 비중**

전체 최적화는 자본이 커진 뒤에 의미가 생긴다.
`log(자본규모)` 상태값이 이 전환을 RL 이 학습하는 경로다.

---

## 7. 검증

- 하방 베타가 낮게 측정된 섹터가 **실제 하락장 구간에서 덜 빠졌는지** 사후 확인
- 리스크 패리티 비중이 동일가중·스코어 비례 대비 MDD 를 낮췄는지
- 위기 공분산 전환이 실제 폭락 구간에서 현금 비중을 올렸는지
- 최적화기 투영이 스코어 상위 종목을 과도하게 깎지 않는지 (알파 손실)
- **팩터 모델의 설명력** — 잔차 분산 비율. 너무 높으면 팩터가 부족한 것

## 그래서 유동성이 1급 제약이 됐다

`universe.min_turnover_20d_kr` 은 지금 **5억원**이다. 그런데 산수를 하면:

    종목당 목표금액 = 최대비중 4.79% × 자본
    ADV 상한       = max_adv_ratio 3% × 20일 평균 거래대금
    안 잘리려면     ADV ≥ 4.79% / 3% × 자본 = 1.6 × 자본

자본 5억이면 **ADV 8억 이상**이라야 최대 비중 종목이 안 잘린다. 하한이 5억이니
**하한을 통과한 종목의 상당수가 애초에 담을 수 없는 종목**이다.

> **하한을 상수로 두는 것이 틀렸다.** 지금 값은 소액 시절에 "못 파는 종목을
> 거른다" 는 뜻이었는데, 자본이 커지면 같은 상수가 전혀 다른 의미가 된다.
> 유동성 하한은 **자본에서 유도해야 한다** — `max_position_weight` 와
> `max_adv_ratio` 와 자본이 이미 그 식을 결정한다.
>
> 다만 하한을 올리면 유니버스가 줄고, 그러면 §1~§3 이 다룰 종목 수가 줄어든다.
> 얼마나 줄어드는지 재 보고 정할 일이다 — 이 부록에서 값을 정하지 않는다.

## 1단계 — 유동성 하한을 자본에서 유도했다 (2026-08-22)

`universe.turnover_capacity_multiple` 을 새로 뒀다(기본 1.6). 실효 하한은
`max(min_turnover_20d_kr, multiple × 자본)` 이고, `filters.py` 의
`FilterParams.effective_floor` 이 낸다. **KR 에만** 건다 — 자본은 원화, KR
거래대금도 원화라 바로 비교되지만 US 거래대금은 달러라 환산이 필요하다.

배수를 1.6 으로 정한 근거는 실측이다(`tools/measure_liquidity_floor.py`,
자본 5억):

    상수 5억   통과 1208 · 최대비중(15%) 용량충족 48%   ← 절반이 잘린다
    1.6×(8억)  통과  997 · 용량충족 58%                ← 채택
    3.0×(15억) 통과  738 · 용량충족 78%
    5.0×(25억) 통과  579 · 용량충족 100%

5.0× 는 15% 캡을 전부 보장하지만 유니버스를 절반으로 깎는다. **실현 최대비중은
4.79% 로 15% 캡에 닿은 적이 없어**(2026-08 실측), 있지도 않은 캡을 지키려

빠진 종목의 이유를 둘로 가른다: 상수(5억) 미달은 **"거래대금 하한 미달"**(못
파는 종목), 배수까지 올린 하한 미달은 **"거래대금 용량 미달"**(못 사는 종목).

## 2단계 — 섹터 상·하방 베타를 측정했다 (2026-08-22)

`portfolio/sector_beta.py`. 시장 하락일만 골라 `cov/var` 로 하방 베타를,
상승일로 상방 베타를 낸다. 섹터 수익률은 KSIC 24섹터의 **시총가중** 합성이고,
가격은 보정 종가다(원주가면 액면분할이 베타를 흔든다). 추정부는 순수 함수로
갈라 창고 없이 검증한다(`betas_from_returns` 등, tests/portfolio).

    제조:식품·음료   하방 0.19  상방 0.03      ← 낮지만 상방도 낮다 = 현금형
    부동산          하방 0.23  상방 0.03
    금융·보험        하방 0.72  상방 0.70      ← 거의 대칭
    제조:전자·전기    하방 1.19  상방 1.35      ← 유일한 고베타 (525종목, 삼성·하이닉스)

**KOSPI 는 사실상 전자 지수다.** 삼성·하이닉스가 지수를 지배해서, 다른
섹터의 "지수 대비 베타" 가 대부분 1 미만으로 나오는 것이 통계 착시가 아니라
사실이다. 지수가 오르면 다른 섹터가 못 따라가고(상방 낮음), 내리면 같이
빠진다(하방 상대적으로 높음).

**비대칭 방어 섹터(하방 낮고 상방 높은)는 하나도 없다.** 하방이 낮은 섹터는
전부 상방도 낮은 **현금형**이었다. 이것이 §4 가 미리 경고한 바로 그 그림이다
— "둘 다 낮으면 그냥 현금과 비슷하고, 그럴 바엔 현금을 드는 게 낫다." 즉
**주식 안의 섹터 로테이션으로는 방어가 안 된다**는 것이 KR 에서 실측으로
확인됐다. 진짜 방어는 현금·통화(원화 자연헤지)라는 §4 의 결론이 데이터로
뒷받침된다.

> 다음(3단계)은 이 상·하방 베타와 팩터 모델(§2)을 리스크 패리티(§3)의
> 공분산 입력으로 넣는다. `is_defensive` 가 비어 있으므로, 3단계의 방어는
> 섹터 선택이 아니라 **현금 비중**으로 나와야 한다.

## 3단계 — 팩터 모델 + Ledoit-Wolf 로 공분산을 냈다 (2026-08-22)

`portfolio/factor_model.py`. 개별 종목 공분산을 직접 추정하지 않고
`Σ = E Ω Eᵀ + diag(D)` 로 조립한다:

    E : 종목×팩터 노출     Ω : 팩터 공분산(LW 축소)     D : 고유분산

**팩터 = 시장 + 24섹터(시장에 직교화).** 시총가중 섹터 합성(§1)을 그대로
쓰면 시장과 겹쳐서, 각 섹터를 시장에 회귀한 **잔차**만 섹터 팩터로 남긴다.
각 종목은 [시장, 자기섹터] 에 시계열 회귀해 로딩을 얻고, 그것을 전체 팩터
공간에 심는다(자기 섹터 열에만 값, 나머지 0). LW 는 정준 2004 판을 직접
뒀다(sklearn 없음).

KR 후보 30종목 실측(`tools/report_factor_model.py`, 창 250):

    공분산 30×30 · PSD (최소 고유값 +1.65e-4)
    팩터 11개 실림 (MKT + 섹터 10)
    LW 축소 강도 0.069        ← 250표본·11팩터라 표본공분산이 이미 안정적
    고유분산 비율 중앙값 0.65  ← 절반 넘게 시장·섹터로 설명 안 됨

**고유분산 비율 0.65 가 §7 이 말한 그 신호다** — "잔차 분산 비율이 너무
높으면 팩터가 부족한 것". 시장+섹터만으로는 소형주 개별 움직임의 65% 가
안 잡힌다. 이것이 **스타일 팩터(시총·밸류·모멘텀·변동성)를 붙여야 하는
데이터 근거**다.

### 스타일 팩터는 후속으로 미뤘다 — 왜

§2 는 시총·밸류·모멘텀·변동성도 팩터로 든다. 그것들은 **매 세션의 종목별
표준화 노출 패널**이 있어야 팩터 수익률(일별 횡단면 회귀 계수)을 낼 수
있는데, 지금 그 패널을 싸게 만들 경로가 없다(IC 캐시는 규격이 다르다).
시장+섹터만으로도 공통 등락과 업종 군집은 잡혀서 §3 리스크 패리티를 시작할
수 있다. 스타일은 그 패널이 생기면 이 모듈의 **팩터 축만 늘려** 붙인다 —
`Σ = EΩEᵀ + D` 구조는 그대로다.

> 다음(4단계)은 이 Σ 로 리스크 기여를 균등화하고(§3) 스코어로 틸트한다.
> 고유분산이 크다는 것은 리스크 패리티가 **섹터보다 종목 단위 분산**에 더
> 의지하게 된다는 뜻이다 — 그것대로 맞는 방향이다.

## 4단계 — 리스크 기여 균등 + 스코어 틸트 + 제약 투영 (2026-08-22)

§3 의 알고리즘 세 조각을 다 만들었다. **배선(allocator 에 끼우기)은 아직**
이다 — 그건 아래 "6단계 = §5" 와 얽혀 있어 따로 한다.

**1~2단계 (`portfolio/risk_parity.py`).** 금액이 아니라 위험을 나눈다.

- `risk_budget_weights`: Spinu 볼록화를 좌표하강으로 푼다. RC_i ∝ 예산.
- `sector_budgets`: b_i = 1/(섹터수·섹터크기) → **섹터 RC 를 균등화**한다.
  반도체 3종 + 통신 1종이면 섹터 RC 가 각 0.5(종목 수와 무관). §3 이 경계한
  "상위 20종목이 전부 반도체" 를 이 예산이 막는다.
- `score_tilt`: w ∝ 기준선 × exp(`score_tilt`·score). RL 할인율 `gamma` 와
  이름을 나눴다 — 충돌하면 진화가 엉뚱한 손잡이를 돌린다. 진화 탐색 대상.

**3단계 (`portfolio/constraints.py`).** 기준선을 덮어쓰지 않고 위반한 만큼만
경계로 당긴다.

    단일 종목 RC   ≤ 0.15      섹터 RC   ≤ 0.35
    하방 베타 가중평균 ≤ 1.0    현금 하한  ≥ (레짐, 호출자가 준다)

RC 상한은 비선형이라(w 하나 바꾸면 전부 바뀜) √ 감쇠 반복으로 건다. 하방
베타는 exp(−λ·베타) 이분 탐색으로 저베타에 민다. **상한은 실현 가능해야
한다** — RC 합은 1 이라 종목 상한 c 면 1/c 종목 이상 필요(0.15→7종목).

KR 24종목 실측(투영 전 → 후):

    최대 비중     0.419 → 0.213
    종목 RC 최대  0.376 → 0.150  (≤0.15)
    섹터 RC 최대  0.376 → 0.166  (≤0.35)
    하방베타 avg  0.31  → 0.42   (≤1.0)
    합            1.00  → 0.95   (현금 5%)

**최대 비중 0.213 인데 종목 RC 0.15 다.** 저변동성 종목은 비중이 커도 위험
기여는 상한 이하 — 이것이 §부록이 말한 "섹터 상한을 개수에서 **리스크
기여로** 옮긴다" 다. `max_position_weight`(비중 상한) 는 이 설계와 충돌하므로,
배선 때 RC 상한이 그것을 **대체**한다(비중이 아니라 위험을 조인다).

## 6a단계 — 룰 베이스라인 배선 (2026-08-22)

`Baseline.RISK_PARITY` 를 추가하고 `allocator/risk_parity_baseline.py` 로
§1~§3 을 이어 붙였다. `session/daily.py` 가 baseline 값을 보고 갈라 부른다 —
`risk_parity` 면 창고에서 공분산·섹터·하방 베타를 세워 `construct_baseline`
+ `project` 로, 아니면 기존 순수 `allocate` 로.

**기본값은 `score` 그대로다.** risk_parity 는 세션마다 팩터 모델을 세워
백테스트 핫패스가 무거워지므로 opt-in 으로 둔다. 팩터 모델이 못 서면
스코어 비례로 물러서고 그 사실을 로그 driver(`risk_parity:fallback`)에 남긴다.

배선에서 정한 것 둘:

- **현금은 여기서 안 뺀다**(`cash_floor=0`). 레짐 현금은 뒤의 `exposure.apply`
  한 곳이 정한다 — 투영에서도 빼면 이중으로 빠진다.
- **RC 상한이 `max_position_weight` 를 대체한다.** risk_parity 경로는
  `_normalize`(비중 상한)를 안 타고 `project`(RC 상한)를 탄다. 비중 21%라도
  위험 기여 15% 면 통과 — 이것이 "금액이 아니라 위험" 의 결론이다.

새 config 키 다섯(`allocator.score_tilt`·`name_risk_cap`·`sector_risk_cap`·
`downside_beta_cap`·`risk_window`)은 **RL 캐시 지문에 넣었다.** RL env 가
직접 읽진 않지만 cache.py→session.daily→risk_parity_baseline 으로 import
닫힘이 닿고(test_cache_config_scope), risk_parity 로 학습하면 이 값이
베이스라인을 바꾼다 — score_tilt 는 진화 유전자가 될 값이라 특히 그렇다.

### 남은 것 — §5 RL 상태값 (6b단계)

RL 이 이 최적화기를 **뒤가 아니라 앞에** 써야 한다(§5). Risk Analyst 가
팩터 노출·하방 베타·섹터 RC 를 상태값으로 내보내고, RL 이 그것을 보며 비중을
내고, Executor 가 위반 시에만 최소 투영을 한다. 그건 카나리가 갈린 뒤다 —
2026-08-22 카나리에서 정답을 줘도 비중 머리가 안 배웠다. 배선(6a)이 끝난
지금, 6b 는 그 위에 상태 차원을 얹는 일이라 카나리 판정을 흐리지 않게
순서를 지킨다.

## 지금 섹터 상한은 개수 기준이다 — 문서가 요구하는 것이 아니다

`candidates.select` 가 거는 것은 `n_candidates 24 × sector_cap 0.35` = **8종목**
이다. "한 섹터에서 8종목까지" 는 걸지만 **"그 섹터가 포트폴리오 위험의 35%를
넘지 않게"** 는 아직 못 건다. 전자는 금액도 변동성도 안 본다.

옮기는 자리가 4단계(§3)다. 그 전까지 개수 기준을 **끄지 않는다** — 없는 것보다
낫고, 지금 처음으로 실제로 걸리기 시작했다.

## §5 는 여전히 카나리 뒤다

2026-08-22 카나리 120업데이트에서 **정답을 줘도 비중 머리가 안 배운다**는 것이
다시 확인됐다(상관 -0.031 → -0.045). 폐기한 가설이 다섯이다. 그 위에 상태값
차원을 더 얹으면 안 배우는 원인이 하나 더 늘 뿐 판정은 더 어려워진다.

**1~5단계는 RL 과 무관하게 M3 룰 베이스라인 위에서 검증된다.** §5 는 그것이
끝나고 카나리가 갈린 뒤에 붙인다. 순서를 바꾸지 않는 것이 §5 의 핵심이기도
하다 — 최적화기를 RL 뒤에 놓으면 액션 반영률이 떨어지고, 그게 선행 프로젝트를
룰 시스템으로 전락시킨 실패 모드다.
